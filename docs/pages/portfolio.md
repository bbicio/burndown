# portfolio.html

Project reporting dashboard (portfolio overview + per-project dashboard), Vue 3 (CDN, no build step, same pattern as `project-config.html`).

This file holds the full implementation narrative for this page — cycle-by-cycle detail, methods involved, first-attempt bugs, and report references. `CLAUDE.md`'s Pages table keeps only a one-line purpose description; when working on this page, read this file, not that row, for the detail. See `/sync-docs`'s routing rule for where future changes to this page should be written.

## Base state

Folds in the former `js/portfolio.js` + `js/dashboard.js` (both now unloaded by this page — `js/dashboard.js` was exclusive to `portfolio.html` and is now fully orphaned dead code; `js/portfolio.js` remains loaded elsewhere, see its own entry in `CLAUDE.md`'s File Structure section). No longer loads `js/roles.js` (confirmed unused) or `js/config-form.js` (only needed for the now-removed, previously-unreachable `#configModal` + nested clients/programs/roles CRUD modals). Adds `js/lib/portfolio-calc.js`. `cardData(cfg)` hoisted into a `cardDataMap` computed (was called ~29x/row per project card). Includes the shared `#confirmModal` markup (2026-07 fix — it was missing from this page even though `js/ai.js`'s `openAiAnalysis()` no-API-key dialog, loaded here, depends on it; `showConfirm()`/`showInfo()` calls from this page silently threw before this fix).

## List-view project cards restructured (2026-09)

The user, using the product as an actual analyst, reported never reading the per-project monthly Estimated/Spent/Variance table shown in each card, always clicking through to the detail page instead; went through a full Brief → brainstorming (with a visual-companion mockup session) → design spec → 4-task plan → subagent-driven-development cycle (`docs/superpowers/specs/2026-09-08-portfolio-list-view-card-restructure-design.md` / `docs/superpowers/plans/2026-09-08-portfolio-list-view-card-restructure.md`).

Each card (grouped-program-child and ungrouped) now shows only identity (title, code, pipeline/status badges, an actuals-availability badge relabeled `No actuals available`, was `no XLS data`) plus a compact stats row — Duration (`monthLabel(cfg.startDate) + ' – ' + monthLabel(cfg.endDate)`), Sold (`cardDataMap[cfg.id].totalPhasing`), Spent (`totalSpent`), Variance (`totalVar`, colored via the unchanged `varColor()`) — no monthly breakdown, no PTC column.

The single remaining button, `Project Dashboard` (was `📊 View Report →`, then `Open project →` until a 2026-09 rename), is now always enabled (previously `:disabled="!hasData"`), since at the time it was the only path into the detail page, which also hosts `📂 Load Actuals` and `＋/✓ Summary` (both added to the detail header's existing Configure/Planning/AI Analysis/Share row, `portfolio.html:205-214`, neither gated on `hasData`).

**`⚙️ Configure` returned to the list cards in a later 2026-09 cycle** (see "List-view search/Status filter + Configure button" below) — the original "detail-only, deliberately not kept" decision was explicitly reversed on user request; treat that decision as superseded, not as a description of current behavior.

Cards render in a 2-column Bootstrap grid (`row g-3`/`col-md-6`/`col-12` — no new CSS class introduced anywhere in this change) — a program group spans the full row width and its own children render in a nested `row g-3` of their own; render order is unchanged (`visibleProgramGroups` then `ungroupedProjects`), CSS grid auto-flow handles the full-width/half-width mix without any reordering logic.

`kpiLeftColor()` (detail-view `Hours Left`/`Budget Left` KPI cards) gained an explicit `var(--color-success)` branch for a positive residual — previously fell through to a neutral color, unlike the list view's own `varColor()`, which was already green/red — aligning the two views' variance-color convention.

A whole-branch code review (post per-task reviews, which don't see cross-task integration) caught two further fixes folded into the same cycle: the Chart.js burndown chart on the detail page is now explicitly redrawn (`this.$nextTick(() => this.renderBurndownChart())`) after an actuals upload that happens while already on that page — previously stale, a path that didn't exist before Load Actuals moved there; and the detail page's own project-switcher dropdown (`dashboardSiblings`) no longer disables (`hasActuals`-gated) siblings with no actuals — the same restriction this whole redesign was removing elsewhere — with its label falling back to the project's own code (e.g. `HITA...`) before the raw DB UUID (`{{ s.name || s.code || s.id }}`) rather than ever surfacing the UUID to a user.

`cardData()`'s returned object is now trimmed to only what the new card markup reads (`hasData`, `hasPhasing`, `totalSpent`, `totalPhasing`, `totalVar`, `budgetBadgeHtml`) — `months`/`monthSpend`/`totalPtc` dropped as dead (still computed as internal locals where still needed); `varCellStyle`/`varCellText` (the old table cells' per-month color/text helpers) deleted outright, fully unreferenced.

## Cold-review follow-up (2026-09-09)

3 issues found by the user's own manual testing of the merged redesign, fixed in the same style:

1. The program-group header row (e.g. "Menarini Ricerche") kept its old per-month Program Summary table — originally an explicit excluded-scope decision from brainstorming, extended on request to match the individual cards' Duration/Sold/Spent/Variance stats row, aggregated across all children via `programSummary()` (now trimmed to `{ grandEst, grandSpent, grandVar }`, same dead-field pattern as `cardData()`) and a new `programDuration(cfgs)` helper (min start / max end across children's `startDate`/`endDate`, lexicographic-sort-safe since `YYYYMM` is fixed-width); the "N projects" badge stays exactly where it already was, in the header row itself, untouched by the table's removal. Both `programSummary(prog.children)`/`programDuration(prog.children)` were initially called directly from the template (up to 4x/3x per program per render) — a follow-up review flagged this against the file's own `cardDataMap` precedent, so they're now hoisted into a `programStatsMap` computed, keyed by `prog.id`.
2. `showDashboard(pid)`/`showOverview()` — this page's own in-app navigation, used by the card's `Open project →` and the sibling-switcher dropdown — never touched the URL, unlike every other entry point into this same detail view (`pipeline.html`/`costgrid.html`/`planning.html`/`project-config.html`'s save-redirect, all of which navigate via `window.location.href = '/portfolio.html?projectId=...'`); now calls `history.replaceState(null, '', '/portfolio.html?projectId=' + encodeURIComponent(pid))` / bare `'/portfolio.html'` (matching this codebase's one existing precedent for the pattern, `js/costgrid.js:1006`; `replaceState` not `pushState` since there's no `popstate` handler anywhere in this codebase and a full back/forward SPA router was judged out of scope).
3. The detail page's title area still showed the raw DB UUID (`{{ dashboardProject?.name ? dashboardProjectId : '' }}`) whenever the project had a name — the same bug already fixed for the sibling dropdown in the prior cycle, missed here; now reads `dashboardProject?.code`, same `v-if="code && name"` guard as the dropdown.

Also removed 3 now-dead CSS tokens (`--portfolio-violet-totals-bg`/`-row-bg`/`-row2-bg`, `css/tokens.css`) whose only consumer was the removed program table — `--portfolio-violet-tint-bg` (the "N projects" badge) stays, still live.

## List-view search/Status filter + Configure button (2026-09)

The list view's filter row (`Sort`/`Client`, `portfolio.html:41-71`) gained, in this order, a free-text search input (`portfolioSearch`, first in the row — matches project name, project code, and client name case-insensitively; skips the client-name term entirely for an unassigned client rather than matching every such project on the literal word "Unassigned") and a Status multi-select checkbox dropdown (`portfolioStatusFilter`, same UI idiom as `pipeline.html`'s Owner/Client/Currency/Value filter-bar dropdowns — `data-bs-auto-close="outside"`, count badge; a fixed `statusFilterOptions` computed returns all 5 `project.status` values verbatim from `js/lib/status-rules.js`, not derived from live data since the enum is fixed).

Both feed two more `.filter()` clauses on the existing `sortedFilteredProjects` computed (AND with the pre-existing Client filter; multiple checked Status values combine via OR; an empty/missing `p.status` matches "Not started yet", mirroring `statusBadgeLarge()`'s own default in `js/core.js` — matching the *badge shown on the card*, not the raw stored value, was the one real bug caught by code review here).

A `portfolioFiltersActive` computed (search/Client/Status only — deliberately excludes Sort, a display-order control) gates a "✕ Clear filters" link (`clearPortfolioFilters()`) and an empty-state alert ("No projects match the current filters.") shown when `visibleProgramGroups`/`ungroupedProjects` are both empty.

Program groups now auto-expand (`v-if="expandedPrograms.has(prog.id) || portfolioFiltersActive"` on the children block) whenever any filter is active, so a matching child project is never hidden behind a manual "Show Child Projects" click — the manual toggle button itself is hidden (`v-if="!portfolioFiltersActive"`) and replaced by a non-interactive "▼ Shown (filtered)" badge while a filter is active, since a first attempt left the toggle clickable-but-inert in that state, and the click still silently mutated `expandedPrograms`, so clearing filters afterward could leave a group's manual expand/collapse state flipped from what the user last clicked.

Each card (grouped-child and ungrouped) also gained a `⚙️ Configure` button next to `Project Dashboard`, reusing the pre-existing `goConfigure(id)` method unchanged (navigates to `/project-config.html?projectId=<id>`), gated `v-if="cfg.my_permission !== 'viewer'"` — identical gating to the detail view's own pre-existing Configure button one section below. No `js/*.js`/`js/lib/*.js` files touched; no cache-bust bump needed.

## Summary by task/role/functional area — task-precise reconciliation (2026-09)

The per-project detail page's timesheet summary cards (`summaryByTask()`/`summaryByRole()`/`summaryByGroup()`, plus `buildSummaryCols()`/`summaryTotals()` — the last two extracted to `js/lib/portfolio-calc.js`, vitest-covered) reconcile role-level tariffs correctly now that a role's `hourlyRate` is configured per `(task, role)` pair (`task_roles.rate_override`), not globally per role — verified against the real Bayer AG "BERMITS Maintenance 2026" project, where role "HWGACCSVS - DIRECTOR" resolves to 168/h on task "Overall Coordination" and 130/h on "Project Management" (via `findRate()`'s task-scoped matching with a fallback-to-first-resource behavior when the raw uploaded timesheet's role text doesn't exactly match a task's configured resource).

"Summary by task" (unchanged, groups by task alone) and "Task detail" (unchanged, per-task role breakdown) were already correct. "Summary by role" now keys by a composite `role|task` string — one column per (role, task) pair actually present, so a role billed at two different tariffs on two different tasks gets two separate, internally-consistent columns instead of one blended one.

"Summary by functional area" (`cfg.groups[]`) took a different path after a first attempt (also splitting by task) turned out to make it collapse to nearly the same column count as "Summary by role" whenever a group had only one active member-role per task — losing its value as a coarser rollup: each group's `roles: string[]` (a flat role-name list, matched against *any* task using that role) became `entries: [{role, task}]` (`normalizeGroupEntries()`/`entryMatchesRow()`, `js/lib/portfolio-calc.js`), where `task === ''` is a wildcard preserving the old "any task" behavior — a group can now claim a role's hours on one specific task while leaving that same role's hours on a different task (billed at a different rate) out entirely, so the card stays **one column per area** while still being precise.

No DB migration: a group with only legacy `roles: string[]` and no `entries` normalizes to all-wildcard entries transparently, in both `project-config.html` (on load, `resolveProject()`) and `portfolio.html` (in `summaryByGroup()` itself) — existing group definitions keep working unchanged until re-edited. `project-config.html`'s "7. Functional Groups" form (previously a single role-name-per-line textarea) is now per-role rows: a role text input plus a task `<select>` (options = the project's own tasks, plus "— any task —" for the wildcard); `onSave()` drops any row left with a blank/whitespace-only role before saving.

Cache-bust: `js/lib/portfolio-calc.js?v=1` → `?v=3` across this cycle.

## Symmetric back-navigation (2026-09)

The detail view's top `← Portfolio` button (`showOverview`) is now duplicated at the bottom of the page too, after Task detail — both call the same unchanged method; the bottom one carries `mt-4 mb-4` so it isn't flush against the footer. A first attempt placed the new bottom button *after* the dashboard's own `<template v-else>` closing tag instead of before it, making it an unconditional sibling of both view templates (rendered on the list view too, not just the dashboard) — caught during manual verification, not by any automated check, and fixed by moving it inside the block.
