# planning.html

Resource planning (filters, By Role/By Project/By Owner grouping views, monthly/weekly interval, monthly pulse, rounded-hours toggle, XLS export/upload, Team assistant panel for admins), Vue 3 (CDN, no build step, same pattern as `pipeline.html`/`costgrid.html`).

This file holds the full implementation narrative for this page — cycle-by-cycle detail, methods involved, first-attempt bugs, and report references. `CLAUDE.md`'s Pages table keeps only a one-line purpose description; when working on this page, read this file, not that row, for the detail. See `/sync-docs`'s routing rule for where future changes to this page should be written.

## Base state

Last Tier 2 page in the Vue migration roadmap — every page except the 10-line `index.html` redirect is now on Vue 3. Folds in the former `js/planning.js` (1558 lines, now deleted — confirmed exclusive to this page, same precedent as `js/pipeline-board.js`/`js/dashboard.js`); single monolithic `Vue.createApp`, no sub-components. Adds 4 new `js/lib/planning-calc.js` exports (`getCalendarWeeks`/`workingDaysInWeek`/`getPlanningPeriods`/`countFutureTaskWeeks`, see `js/lib/` entry in `CLAUDE.md`). Drops the `js/config-form.js` and `js/costgrid.js` `<script>` tags (confirmed dead on this page — no reachable `#configModal`, and no genuine call into `costgrid.js` beyond two page-local no-op overrides), files themselves untouched since still loaded elsewhere. Keeps `js/roles.js`/`js/clients.js`/`js/programs.js` loaded unmodified (their `load*FromApi()` calls are genuinely used; their CRUD-modal dead markup — `#rolesModal`/`#roleModal` — was already removed, same cleanup as `costgrid.html`'s cycle) and `js/upload.js`/`js/portfolio.js` loaded unmodified as globals (`js/ai.js`, which used to be loaded here for the AI Planning Sidebar, was deleted in Cycle B, 2026-09-30, see "Team assistant" below). `created()` awaits `initNav()` and returns early on `!user` before any API-loading call, matching every other migrated page's pattern (a Gate-3 code-review fix — the first draft inverted this ordering). `initTooltipsAndToggles()` guards every `addEventListener` call with a `data-pp-bound` marker so re-invocations across `updated()` (which fires on every reactive re-render, e.g. chat keystrokes) never double-bind a `v-html`-rendered row left in place.

"Export XLS" (`buildStyledExcelExport()`) — a pre-existing bug found during this cycle, `ReferenceError: ExcelJS is not defined` since no page loaded the ExcelJS library — was fixed in a later dedicated cycle (2026-07-28) by adding the ExcelJS CDN `<script>` tag to this page (and to `costgrid.html`, for `cgExportXls()`); both pages also loaded `xlsx@0.18.5` (SheetJS) via CDN, confirmed genuinely unused by any client-side JS on either page (XLS upload/parsing goes entirely through the backend API) and removed in a later cleanup cycle (2026-08-01) — `portfolio.html` and `project-config.html` still load it for their own genuine uses and are unaffected.

## By Role project/task drill-down (2026-09)

Deferred from the `portfolio.html` role/task-dimension cycle per explicit user decision (that cycle fixed the analogous "same role, multiple tasks blended together" issue for `portfolio.html`'s Summary cards; this one is the corresponding fix for `planning.html`'s hours-only By Role view). Each role row in `byRoleView()` gains the same collapse/expand toggle already used by By Project/By Owner (`.pp-toggle` ▼/▶, `data-group-id`/`data-parent-group`, wired through the existing `initTooltipsAndToggles()`), **collapsed by default** — unlike By Project/By Owner, which default to expanded (no inline `display` style on their child rows). Expanding a role row reveals one child row per (project, task) combination it covers, with its own Sold/From actuals/To be planned and period cells scoped to just that pair; the parent role row's own aggregate is unchanged.

Data comes from a new `roleChildMap` accumulator built alongside the existing `roleSoldMap`/`roleActualsMap` at the same point in `byRoleView()`'s forEach (same `soldH`/`consumedH` values, just also kept partitioned per (project, task) instead of only merged into the role-wide total); per-period child hours are derived from `js/lib/planning-calc.js`'s new `sumChildBreakdownHours(roleWeekMap, weekKeys, project, task)` (pure, vitest-covered), which filters the same `breakdown: [{project, task, hours}]` entries the parent row's own tooltip already used. "Expand all"/"Collapse all" buttons were added to By Role's own toolbar (previously only on By Project/By Owner).

Because By Project/By Owner had never shipped a default-collapsed group before, `initTooltipsAndToggles()`'s group-bootstrap line (inside that method) was generalized to seed each group's `collapsed` state from its child rows' actual current DOM `display` value instead of hardcoding `false` — otherwise the first click on a default-collapsed group after any re-render would be a no-op (the internal bookkeeping and the real DOM would disagree). Verified manually that unrounded child-row Sold/Actuals/To-be-planned sum exactly to their parent role's totals (the "Rounded" toggle's independent per-cell rounding can make the *rounded, displayed* child sum differ by ±1-2h from the parent — a pre-existing characteristic of that toggle throughout this file, not a bug).

Cache-bust: `js/lib/planning-calc.js?v=2` → `?v=3`.

## Inactive-owner handling (2026-09)

Future ("to be planned") hours are no longer split with owners who are `inactive` in the `resources` registry — their share is redistributed proportionally among the remaining active (or unmatched/ambiguous, which count as active) owners on that task+role; if every owner on a task+role is inactive, its entire future share falls to the existing TBD placeholder row. Past actuals are never affected — an inactive owner's historical hours display exactly as before, with a small "inactive" badge next to their name (By Project drill-down, By Owner view, and both views' XLS exports).

Status resolution reuses Cycle 3b's `api/src/lib/match-resource.js` matching (`normalizeName`/`buildMatchContext`/`matchOwner`) via a new `POST /api/resources/match-owners` route (removed in Cycle B) — `requireAuth` only, not `requireAdmin` (deliberately declared above `resources.js`'s blanket admin gate), since Planning is visible to every authenticated user and the response carries no PII, just a name→status map. Only an exact, unambiguous match to a currently-inactive resource resolves to `inactive`; an unmatched, ambiguous, or explicitly-ignored name resolves to `active` (same "when in doubt, don't touch anything a person is actively counting on" posture as the rest of this feature).

The redistribution math itself is a new pure function, `redistributeExcludingInactive(ownerTotals, ownerStatus)` in `js/lib/planning-calc.js` (vitest-covered), consumed by both `byProjectView` and `byOwnerView`'s existing proportional-split code — replacing their previous raw `ownerTotals[o]/totalOwnerH` math in the `distribute` closures and `ownerProp` calcs. `planning.html` fetches the status map once per page load (`refreshOwnerStatuses()`, called from `created()` and again after an XLS upload) and fails open — treats every owner as active — if the fetch fails, so this is purely additive: it can only ever narrow which owners receive future hours, never break the page.

**Findings closed during `/finish-cycle` review, not in the original plan:**
- **All-inactive TBD row (plan defect, caught mid-execution):** the plan's own Step 2b claimed `displayOwners` needed no change, but the design spec requires a *visible* TBD row when every owner on a task+role is inactive, not just a correct role-level total. `displayOwners` was corrected to `hasOwners ? (allOwnersInactive ? (ownerNames.includes('—') ? ownerNames : [...ownerNames, '—']) : ownerNames) : ['—']` in both views — the `includes('—')` guard also makes the append idempotent, closing a related theoretical double-count when a genuine blank-owner actuals row coexists with the all-inactive case.
- **`byOwnerView` owner-set mismatch (final review, Important):** `ownerNames`/`displayOwners` are filtered to owners with >0.01 actual hours, but `redistributeExcludingInactive` was originally called with the unfiltered `ownerTotals` — a near-zero owner could receive a computed future-hours share that was never added to any displayed total, silently understating the view's summed "To be planned". Fixed by pre-filtering `ownerTotals` to the same >0.01 threshold before the redistribution call.
- **Blank-owner (`'—'`) placeholder regression (final review, Important):** the placeholder `ownerProp` formula originally forced *any* `'—'`-keyed row to 0 future hours unless every owner was inactive — but `'—'` is also the key for a genuine blank-owner actuals row, which should still get its own computed share when real named owners are active alongside it. Fixed to `isPlaceholder && (allOwnersInactive || totalOwnerH <= 0.01) ? 1 : (ownerFutureProps[ownerName] || 0)`, distinguishing the synthetic all-inactive TBD case from a real blank-owner row.
- **By Owner Sold-hours carve-out (round 2 code review, deliberate scope expansion beyond the original spec):** `byOwnerView`'s `ownerSold` had always scaled with the same proportion as future hours (pre-existing, spec-documented as intentional). Round 2 review flagged this as counter-intuitive once inactive-exclusion entered the mix — an inactive owner could show `Sold=0` next to nonzero `Actuals`. Sold now uses a separate `ownerActualsProp` (the original, inactive-agnostic `ownerTotals[o]/totalOwnerH` formula, unchanged from before this cycle) so Sold keeps moving with each owner's real actuals share regardless of status; only `ownerTbpH` (future hours) uses the inactive-excluding proportion.
- **Badge markup deduplication (round 1 code review, Minor):** the "inactive" badge's inline-style HTML was duplicated 4 times; extracted into a shared `INACTIVE_BADGE_HTML` constant + `inactiveBadgeSuffix()` helper, both defined once in `planning.html`'s outer `DOMContentLoaded` closure.
- **Backend caching (round 1 code review, Minor):** `POST /api/resources/match-owners` now caches the `resources`/`resource_aliases` query results in-process for 30s (`getResourcesAndAliasesCached()`, removed in Cycle B) instead of re-querying both tables on every page load/XLS upload; invalidated immediately by `rescanAll()` on any resource/alias write. See `docs/api/resources.md`.

**Accepted as follow-up, not fixed this cycle (round 3 code review, Minor, low likelihood at this project's actual scale):** the 2000-name cap on `POST /match-owners` (route removed in Cycle B) could theoretically be hit on a very large deployment (and the frontend doesn't normalize names before the uniqueness check, so case variants count separately), with a silent fail-open (no visible error) if it 400s; the 30s cache has no in-flight request de-duplication, so a burst of concurrent requests right at cache expiry can each trigger their own DB query instead of one.

Cache-bust: `js/lib/planning-calc.js?v=4` (bumped this cycle; see the file itself for the current value).

**Superseded by the Planning model cycle below:** owner status no longer comes from `POST /api/resources/match-owners` / `refreshOwnerStatuses()` (both callers removed; the route and its `getResourcesAndAliasesCached()` cache were deleted in Cycle B) and the redistribution math now runs on the server (`redistributeExcludingInactive` lives in `api/src/lib/planning-distribution.js`); the behaviour described in this section is unchanged.

## Planning model (Cycle A, 2026-09)

The calculation behind the three views moved to the backend: `POST /api/planning/model`, full contract, per-view rules, cache, calendar semantics and verification in [docs/api/planning-model.md](../api/planning-model.md). The page now only fetches and renders.

**How the page loads the model.** Only the ACTIVE view is fetched. `modelRequest` (computed) builds the request via `buildModelRequest` from `js/lib/planning-model-ui.js`: view, ids of the filtered projects, sorted team filters, the visible window (`windowStart`/`windowEnd`) as local `YYYY-MM-DD`, today's local date as `asOf`, and the Monthly Pulse flag; it depends on `refreshTick` (bumped after an XLS upload) and returns `null` for a missing or inverted window (no fetch; the views show their empty state). A watcher on `modelRequest` calls `loadModel()`, which POSTs the request and stores `model = { view, data, keyMap, key: JSON.stringify(req) }`. A stale-response guard (`modelSeq`: a response whose sequence number is no longer the latest is dropped) prevents an old request overwriting a newer one; `modelPending` / `modelError` drive a "Loading planning data…" or red error placeholder (`modelPlaceholderHtml()`), and `exportCurrentView()` does nothing while loading or after a failure. Each view does `adaptRoleModel` / `adaptProjectModel` / `adaptOwnerModel(model.data, model.keyMap)`, which re-key the server's `YYYY-MM-DD` week keys to `weekStart.toISOString()` and reshape the projection into the structures the existing render code already used. `ownerStatusMap` now comes from the response's `ownerStatus` and is used for the "inactive" badges only.

**What stayed in the browser:** project/team/status filters (they only choose which ids and teams are sent), the window and interval (weekly/monthly) paging, period aggregation of the week cells, the Rounded toggle, the HTML of the three views, drill-down toggles, and XLS export (built from the same `exportRows`/`periodMeta`). The HTML/export code of the three views is unchanged.

**Removed:** the browser-side calculation blocks of the three views, `refreshOwnerStatuses()` and its call to `POST /api/resources/match-owners` (the route itself was removed in Cycle B). `js/lib/planning-calc.js` (`?v=5`) lost `distributeFutureResidual`, `redistributeExcludingInactive` and `countFutureTaskWeeks` (see `docs/js/lib.md`). `refreshTimesheetDataFromApi()` is still called on load, now only to keep the shared `timesheetData` cache populated for `js/upload.js` (`js/ai.js` is gone; the call is a removal candidate).

**Behaviour change (Phase 2, By Role only, deliberate and user-approved):** a task's monthly distribution no longer depends on the visible window, so in narrow windows the By Role "To be planned" column can be smaller than before (hours outside the window are no longer re-scaled onto the visible months) and tooltips no longer list zero-hour lines for months beyond the distribution. Everything else is identical to the old page: the Phase 1 parity capture matched 144/144 combinations, and after Phase 2 only the 28 By Role combinations differ. The known Sunday quirk (By Role/By Project do not place an actuals row dated on a Sunday in any week cell, though it counts in the totals) was replicated on purpose and is a deliberate follow-up fix.

Cache-bust: `planning-calc.js?v=5`, new `planning-model-ui.js?v=1`.

## Team assistant (Cycle B, 2026-09-30)

Replaces the old AI Planning Sidebar (personal API keys in the browser, `js/ai.js`, `aiPlanSend`, all removed). Backend, formulas and deploy notes: [docs/api/planning-assistant.md](../api/planning-assistant.md); pure helpers: `js/lib/team-assistant-ui.js` (`docs/js/lib.md`).

- **Who sees it.** A "🤖 Team assistant" button in the toolbar, rendered only for admin or sysadmin (`isAdminUser`); a plain user never sees it and the API answers 403. The button toggles a side panel (`#teamAssistantPanel`, `taOpen`).
- **Project selector.** Lists the projects the page already has (`projectOptions(eligibleProjects)`): those with at least one not-completed task with a role and sold hours above 0. Changing the project starts a new chat (`taNewChat()`: clears messages, tables, params and roles). An empty selection shows the prompt "What do you want to do? Pick a project already in Planning, then ask for a team or press "Calculate team"".
- **"Calculate team"** calls `POST /api/planning-assistant/rank` with `{ projectId, asOf: <local date>, params }` (deterministic, no LLM; works without an API key). "New chat" resets the conversation.
- **Chat.** Starter prompts (`starterPrompts(taRoles)`, filled from the roles of the last result) appear while the conversation is empty and only fill the input. Enter sends (Shift+Enter is a new line); the conversation and the current `taParams` go to `POST /api/planning-assistant/chat`. The reply is shown through `renderChatText` (escaped, only bold and line breaks). The returned `params` are kept and sent back next time, so constraints persist; a failed call adds an apology message and leaves "Calculate team" available. Tables are replaced only when the response carries them (`tables` is `null` when the model did not rank).
- **Three tables.** "Best team", "Alternative team", "Available team" (`tableTitle`), one section per required role, rows formatted by `rowView` (score, hours as the role, tags, similar projects, tasks, topics, free hours average/min, current load, hours on the project, flags, rationale). The error line (`taError`) shows a failed `/rank` (400/404/422 messages come from the API).
- **Page changes around it.** `js/ai.js` and its hidden DOM compatibility elements are gone; `js/lib/team-assistant-ui.js?v=3` is loaded as a module; `css/style.css` holds the panel styles (`.ta-*`, `?v=` bumped on every page).
- **Selection and Enter fixes (2026-09-30).** A `taProjectOptions` watcher resets `taProjectId` and calls `taNewChat()` when `selectionStillValid(taProjectId, taProjectOptions)` turns false (a page filter removed the selected project). The textarea sends only when `shouldSendOnEnter(e)` (Enter, no Shift, not `isComposing`, `keyCode !== 229`). Both helpers are in `js/lib/team-assistant-ui.js` (now `?v=3`). The browser check of this wiring was deferred for lack of Planning data (test case PA-M7/PA-M8).
