# project-config.html

Full-page project config form (tasks, phasing, planning, groups), Vue 3 (CDN, no build step, same pattern as `admin.html`).

This file holds the full implementation narrative for this page — cycle-by-cycle detail, methods involved, first-attempt bugs, and report references. `CLAUDE.md`'s Pages table keeps only a one-line purpose description; when working on this page, read this file, not that row, for the detail. See `/sync-docs`'s routing rule for where future changes to this page should be written.

## Base state

Single reactive project object, not an array; unknown `?projectId=` shows an explicit not-found state instead of falling back to a random project. No longer loads `js/config-form.js` or `js/roles.js`. Page-title-bar (matching `portfolio.html`/`pipeline.html`) shows the project's name (or "New Project" via `isNewProject` for the no-`?projectId=` creation flow). `resolveProject()` normalizes any task's `monthlyDistribution: null` (seen on real data) to `{}` — the Monthly % distribution grid's `v-model` indexes directly into it.

`saveClientModal()`/`saveProgramModal()` (the nested "+ New client"/"+ New program" modals next to their respective dropdowns) guard against a fast repeat click via a `saving` flag on `clientModal`/`programModal` (2026-08, closing a finding from `docs/superpowers/audits/2026-08-04-double-submit-closing-audit.md`) — set as an explicit `if (this.X.saving) return;` first statement plus `:disabled`/text-swap on the Save button, matching this file's own `onSave()` pattern; previously these two had zero protection of any kind, unlike every other save/submit action in the app.

## Actuals block (2026-09)

Mirrors `timesheets.html`'s View/Fee-Spent/XLSX pattern: `⬆ Upload XLS` renamed `📂 Load Actuals` (exact label match with `portfolio.html`); new `👁 View` opens a Bootstrap `.modal.fade` (this page's own established pattern — `bootstrap.Modal.getOrCreateInstance(el).show()`, not `timesheets.html`'s `v-if="modal.show"` overlay) listing `actuals.exportRows` with Date/Owner/Role/Task/Hours/Notes/Fee/Spent, formatted with `formatMoney(amount, project.currency, currencies)` called directly (the page's former local `fmtMoney` method was removed); `⬇ Export CSV` replaced by `⬇ Download actuals` (ExcelJS `4.4.0` CDN, same 8 columns, filename `Client_Project_ProjectCode_YYYYMMDD.xlsx` via a page-local `buildActualsFilename()`/`sanitize()` — duplicates, rather than reuses, `timesheets.html`'s own `sanitizeForFilename()`, a known accepted minor).

`🗑 Clear XLS data` (previously in "1. Project info", a purely local `clearProjectData()` cache clear with **no server effect**) removed and replaced by `🗑 Delete actuals` in the Actuals block (last position, `v-if="project.code && !isViewer"`) — now a **real** `DELETE /api/timesheets/:projectCode` behind `showConfirm()`; on success sets the "no actuals" UI state directly (mirroring `loadActuals()`'s own empty-result branch verbatim, `esc()`-escaped) instead of re-fetching via `loadActuals()`, specifically to sidestep a discovered pre-existing bug (see `api/src/routes/timesheets.js`'s own entry in `CLAUDE.md`) where an admin's very next `GET /api/timesheets/:projectCode` for a now-empty code 403s; also resets `reforecastVisible = false` directly (same reasoning — `updateReforecastVisibility()` hits the same buggy endpoint) so the `↻ Reforecast from actuals` button doesn't linger visible with nothing to reforecast from.

`onSave()`'s post-save redirect changed from bare `/portfolio.html` to `/portfolio.html?projectId=' + this.project.id` (lands on that project's detail view, same as `📊 View Report →`) — **only actually verified for the edit-existing-project path**; a separate, pre-existing, unrelated bug (`BLANK_PROJECT()` sets `id: ''`, `_pushProjectToApi()`'s `if (!project?.id) return;` guard) means new-project creation via this page's Save has never persisted server-side, so the redirect's new-project case is currently moot — see `docs/superpowers/reports/2026-09-07-worktree-project-config-actuals-block-finish-cycle.md` for the full writeup, this is an open critical roadmap item, not fixed by this cycle.

`onDeleteActuals()` gained an `actuals.deleting` in-flight guard (2026-09 cold-review fix, same idiom as `clientModal.saving`/`programModal.saving`) and `downloadActualsXlsx()` gained a `try/catch` around the ExcelJS workbook-build/blob steps, surfacing failures via `actuals.status` instead of an unhandled rejection — see `api/src/routes/timesheets.js`'s own entry in `CLAUDE.md` for the paired backend fix (the `DELETE` route's non-admin check was matching the wrong column, 403-ing every non-admin delete attempt from this page).

This page's own local `showConfirm()`/`confirmModalOk()` (Promise-based, `resolve`s on the shared `#confirmModal`'s `hidden.bs.modal` event — a structurally different implementation from `js/core.js`'s callback-based `showConfirm()`, not a caller of it) gained a `_confirmClicked` guard on `confirmModalOk()` (2026-09 cold-review fix, mirroring `js/core.js`'s own `clicked` flag) — protects all ~9 `showConfirm()` call sites on this page at once (PTC/task/resource removal, Delete actuals, phasing-empty-warning, reforecast confirms), not just Delete actuals.

Actuals status messages (upload/export/delete success and failure) were consolidated into one `flashActualsStatus(message, cls, ms=4000)` helper that tracks its own `_actualsStatusTimer` and `clearTimeout`s any prior pending one before scheduling a new — closes both a missed-auto-clear gap (the upload-failure path had none before) and a race where two flashes within 4s of each other could have the first's timer wipe the second's still-fresh message; `onActualsFileChange()`'s upload-success path still sets `actuals.status` directly rather than calling the helper, since its auto-clear timer must only start after its own trailing `loadActuals()`/`updateReforecastVisibility()` awaits settle, not immediately — but it now shares the same `_actualsStatusTimer` tracking so it composes correctly with the helper's cancellation.

## "7. Functional Groups" per-role/task rows (2026-09)

The role-name-per-line textarea was replaced by per-role rows (a text input + a task `<select>`, options = `project.tasks`, plus "— any task —" for the wildcard) — see `docs/pages/portfolio.md`'s "Summary by task/role/functional area" section for the full `entries: [{role, task}]` model and why. `resolveProject()` seeds `entries` from a group's legacy `roles: string[]` on load; `onSave()` drops any entry left with a blank/whitespace-only role before saving.

## Symmetric back-navigation (2026-09)

A `← Back to Portfolio` / `← Project Dashboard` button pair now appears both at the top of the page (next to the title, new) and at the bottom (next to the pre-existing `← Back to Portfolio`/Save row, `← Project Dashboard` added). `← Project Dashboard` navigates to `/portfolio.html?projectId=<id>` and is hidden (`v-if="!isNewProject"`) for a not-yet-saved new project; it calls a real Vue method, `goProjectDashboard()`, rather than an inline `@click="window.location...."` expression — a compiled Vue template does not reliably fall back to a bare `window` global from inside its own `with()` block (the same landmine already documented for `openShareModal` elsewhere in this codebase), confirmed by an actual `TypeError` hit during manual verification before the fix.

This page's own local `showConfirm(message, opts = {})` gained an `infoMode` option — when true, renders a single neutral `btn btn-primary` "OK" button (no Cancel, modal title "ℹ️ Info") instead of the default two-button Cancel/red-"Confirm" — since the new blocked-upload message has nothing to actually confirm. `onActualsFileChange()`'s catch block checks `err.data && err.data.inconsistencies` (set by `js/api.js`'s `apiFetch()`, see that file's entry in `CLAUDE.md`) and calls `this.showConfirm(formatUploadInconsistencies(err.data.inconsistencies), { infoMode: true })` instead of the generic `flashActualsStatus()` failure path — see `api/src/routes/timesheets.js`'s entry in `CLAUDE.md` for the backend gate this surfaces.

## Descriptions (profile descriptions cycle, 2026-09-29)

The project header form has a **Description** textarea (`project.description`) and every task card a description textarea (`task.description`), all `:disabled="isViewer"` like the rest of the page (viewers, share permission `viewer`, see them read-only). `loadProject` normalises missing values to `''`. They are saved by the existing `_pushProjectToApi` (`js/api-sync.js`, `?v=18`): `description` on `PATCH /api/projects/:id`, per-task `description` on `PUT /api/projects/:id/tasks`. Changing a description queues the project code for the profile worker; the LLM is never called from a save (`docs/api/profile-engine.md`, topic extraction). "Generate project" in `costgrid.html` copies the proposal's description and each task's description into the new project once; after that they are independent, and migration `027`'s one-shot backfill did the same for existing linked projects (`docs/pages/costgrid.md`). The text feeds the extraction of competence topics for the team profiles (`docs/api/topics.md`).

## Save errors are surfaced (2026-09-30)

`onSave` used to swallow every `_pushProjectToApi` error and redirect anyway, so a failed save looked successful. It now calls `_pushProjectToApiDetailed(project)` (`js/api-sync.js`, `?v=18`), which never throws and resolves to `{ ok, failed: [{ part, error }] }` (`part`: `project` | `tasks` | `phasing` | `ptc` | `planning` | `groups`; if the core upsert fails the sub-resources are not attempted). `summarizePushResult(failed)` (`js/lib/project-push-result.js?v=1`, pure, vitest-covered) turns it into `{ ok, message }`. On failure: `jsonError` = "Save failed: <parts> (was|were) not saved. Fix the issue and press Save again.", `saving = false`, `savedSnapshot` untouched (leave-page prompt stays armed), no redirect, scroll to top; the form keeps its data and Save can be pressed again. Any failed part counts as a failed save (option A chosen at brainstorming; a non-blocking warning was rejected because the user would leave the page with unsaved data). `_pushProjectToApi` is now a wrapper returning `!failed.some(part === 'project')`, i.e. exactly the old contract, so `costgrid.js` (`cgDoGenerateProject`, `addTasksToProject`) is unchanged. The in-memory write-back uses replace-or-push for new projects too, so a retry does not duplicate the project in `config.projects`. Empty sections are pushed too (`Array.isArray`/object checks instead of `length`/`Object.keys` in `_pushProjectToApiDetailed`): clearing all tasks, phasing, PTC, planning or groups now reaches the server, where before the empty section was silently skipped and the old data stayed; only a section absent from the project object (`undefined`/`null`) is left alone. Safe for the other callers because `config.projects` items are always full (`_apiProjectToLocal` normalises the five sections and `GET /api/projects` returns tasks). Covered by `js/api-sync.test.js` (loads the classic script against a fake `Api`). The server-side `PUT /tasks` (DELETE + INSERT, not transactional) is unchanged; a retry from the still-populated form repairs an interrupted run. Test cases PC-23..PC-26.

## Unsaved-changes warning (2026-09-30)

`savedSnapshot` holds `JSON.stringify(this.project)`, taken at the very end of `created()` (after `resolveProject`'s normalisations, just before `ready = true`). A `beforeunload` listener registered at the start of `created()` calls `preventDefault()`/sets `returnValue` when `!isViewer && window.isProjectDirty(savedSnapshot, project)` (`isProjectDirty` in `js/lib/config-form-calc.js?v=2`, pure, vitest-covered). `onSave` refreshes the snapshot right before its `location.href` redirect, so a successful Save never prompts; a Save that throws earlier, or fails on the server (see below), leaves the page dirty. Covers any edit, including Derive/Reforecast results. Tags, actuals upload/delete and the client/program modals persist immediately and live outside `this.project`. Spec `docs/superpowers/specs/2026-09-30-ui-defects-data-loss-design.md`.

## Hardening notes (2026-09-30)

- **Decision D7 (docs only):** `config.projects` in `project-config.html` is a page-level cache. A failed save does not roll it back; this is harmless because the next navigation is a full page load and nothing reached the server.
- `PATCH /api/projects/:id` answers 400 `<field> must be a valid UUID` for a non-UUID `cgVersionId`/`clientId` (null and `''` still unlink; `programId` is VARCHAR and not validated).
- The 403 an admin used to get from `GET /api/timesheets/:code` for a project without actuals is gone: it now answers `200 []` (see [docs/api/timesheets.md](../api/timesheets.md)).
- This page does not pass `skipEmpty` to `_pushProjectToApi`, so clearing a section here still persists.

## Money fields and currency menu (2026-10-01, money centralization cycle)

The Currency menu is built from the active currencies (`currencies` data property filled from `loadCurrenciesFromApi()`, computed `currencyOptions`; a project's own currency is added as an extra `(inactive)` option when it is no longer active, so a save never erases it); `project.currency` is an ISO code (new-project default `'EUR'`). `cfgCurrencyLocale`/the old `fmtMoney`/`parseMoney` were removed: templates call `formatMoney(amount, project.currency, currencies)` directly (exposed on the instance), while `moneyInput(amount)` and `parseMoney(str)` stay as one-line methods over `js/lib/money.js` (input focus/blur helpers). The phasing cells and the PTC Amount show `moneyInput(...)` on focus (`350,28`) and `parseMoney` on blur, so focus + blur no longer multiplies a euro value by 100 (the bug that started the cycle). Changing the currency does not convert amounts or touch a rate; a project's currency is independent of its proposal's (follow-up cycle planned). See `docs/js/lib.md`, `TEST_CASES.md` MN-01..MN-05.
## Currency menu read-only, new-project form redirected (2026-10-01, project currency lock cycle)

The Currency `<select>` is disabled by `currencyLocked` (`isViewer || !isNewProject`): read-only for every existing project, with the hint "Currency cannot be changed here: amounts are not converted yet. Contact a sysadmin if it must be corrected."; only a brand-new project (reachable again only when direct creation is re-enabled) can choose its currency. `resolveProject()` redirects the form without `?projectId=` to `/portfolio.html?notice=direct-creation-disabled` while `DIRECT_PROJECT_CREATION_ENABLED` is false (the form code stays untouched). A project's currency and cgVersionId are re-sent on every save; the server accepts identical values. See `docs/api/lib.md`.
