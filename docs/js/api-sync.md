# js/api-sync.js

In-memory ↔ API sync layer (`cgSyncFromApi`, `loadConfigFromApi`, etc.).

This file holds the full implementation narrative for `js/api-sync.js` — function-by-function detail, cycle-by-cycle fixes, first-attempt bugs. `CLAUDE.md`'s File structure entry keeps only a one-line pointer; when working on this file, read this file, not that line, for the detail. See `/sync-docs`'s routing rule for where future changes to this file should be written.

## Base state

`cgSyncFromApi` stores `myPermission: g.my_permission` on each `_cgStore` entry. `_apiProjectToLocal` maps `my_permission: p.my_permission || 'owner'` and converts ISO currency code → symbol (`EUR→'€'`, `USD→'$'`, `GBP→'£'`) for the form select. `costGridRef: { cgId, versionId } | null` — `cgId` is read directly from `GET /api/projects`'s server-resolved `cg_id` field (a `LEFT JOIN` to `cost_grid_versions` in `api/src/routes/projects.js`), **not** from the in-memory `_cgStore`. `_pushProjectToApi` converts symbol → ISO code before PATCH to satisfy the `currencies` FK constraint — fields not listed here are silently dropped even if returned by the API. `_cgApiVersionToLocal` maps `taskIds` and `taskNames` from `lp.task_ids`/`lp.task_names` on each linked-project entry.

## _resolveCgIdForVersion ReferenceError fix (2026-07)

`cgId` reading was fixed to come from the server-resolved `cg_id` field, not `_resolveCgIdForVersion()`/`_cgStore` (declared only in `js/costgrid.js`), which threw `ReferenceError` on any page that doesn't load that script — `portfolio.html`, `project-config.html` — silently emptying `config.projects` on both. `_resolveCgIdForVersion()` itself was confirmed to have zero remaining callers anywhere in the repo and deleted in a later cleanup cycle (2026-08).

## _pushProjectToApiDetailed and empty sections (2026-09-30)

`_pushProjectToApiDetailed(project)` is the real implementation: it never throws and resolves to `{ ok, failed: [{ part, error }] }` (`part`: `project` | `tasks` | `phasing` | `ptc` | `planning` | `groups`). If the core upsert fails the sub-resources are not attempted. `project-config.html`'s `onSave` uses it to refuse to redirect on a failed save (`docs/pages/project-config.md`, "Save errors are surfaced"). Each sub-resource is pushed whenever the project object carries it, **even when empty** (`Array.isArray` for tasks/ptc/groups, non-null object for phasing/planning): an empty section is how the user clears it, and the old code skipped it (`length`/`Object.keys` checks), leaving the old data on the server. Only an absent (`undefined`/`null`) section is left alone. This relies on `config.projects` items always carrying all five (`_apiProjectToLocal` normalises them, `GET /api/projects` returns tasks). Tests: `js/api-sync.test.js` loads the classic script via `new Function` against a fake `Api`. Closed the same day by the hardening cycle: `_pushProjectToApiDetailed(project, { skipEmpty })` / `_pushProjectToApi(project, opts)` — with `skipEmpty: true` empty sections are not pushed (the behaviour before this fix). Only `js/costgrid.js`'s two callers (`cgDoAddTasksToProject`, `cgDoGenerateProject`) pass it, because they re-send a whole, possibly stale, in-memory project and never edit phasing/PTC/planning/groups; `project-config.html` does not, so clearing a section there still persists (PC-27). Residual, accepted (spec D6): a stale copy holding an older NON-empty section, or the `tasks` list `addTasksToProject` always re-sends, is still last-writer-wins. Tests in `js/api-sync.test.js` (`skipEmpty` cases). `api-sync.js` is `?v=19`.

## _pushProjectToApi return value (2026-09)

`_pushProjectToApi` (since 2026-09-30 a thin wrapper over `_pushProjectToApiDetailed`, returning `!failed.some(part === 'project')`, i.e. the same contract) returns `true`/`false` (was always implicitly `undefined`) — `true` once the core project upsert is confirmed persisted server-side, `false` if that upsert itself failed (sub-resource pushes — tasks/phasing/ptc/planning/groups — stay best-effort/swallowed internally and don't affect this return value); consumed by `js/costgrid.js`'s `cgDoGenerateProject()` to decide whether the post-generation dialog can safely offer to navigate to `project-config.html`.

## Project currency is an ISO code (2026-10-01, money centralization cycle)

`_apiProjectToLocal` keeps the API's code (`currency: p.currency || 'EUR'`) and `_pushProjectToApiDetailed` sends `meta.currency` unchanged: the former symbol<->code translation (`EUR/USD/GBP` <-> `€/$/£`, other codes passed through) is gone, so `project.currency` is an ISO code everywhere in memory and symbols are derived only for display (`js/lib/money.js`'s `currencyInfo`). Cost-grid versions already used codes (`_cgCurrencyFromDb`). No migration: the DB already stored codes. Covered by `js/api-sync.test.js` (`'project currency is an ISO code in memory and on the wire'`). `loadCurrenciesFromApi()` (fills `window.__currencies`) is now also called by `portfolio.html`, `project-config.html` and `planning.html` before their first render. `?v=20`. A save of a symbol would now fail the `currencies` FK; no source of symbols remains (accepted code-review follow-up, 2026-10-01).
## A rule refusal is final (2026-10-01, project currency lock cycle)

`_pushProjectToApiDetailed` used to retry the core upsert as `Api.projects.create` after **any** failure of `Api.projects.update` (it means "the project is not there yet"). A `400` refusal by the project rules (body `code: 'PROJECT_RULE'`, readable as `err.data.code` because `apiFetch` attaches the parsed body) would then end in a duplicate-key error hiding the rule's message, so such a refusal now returns `{ ok: false, failed: [{ part: 'project', error: <message> }] }` without the retry; every other failure still falls back to create. Covered by `js/api-sync.test.js` (`'a refusal by the project rules is final'`). `?v=21`.

## Strict upsert (2026-10-01, new-version-full-copy cycle)

`_cgUpsertVersionToApi(cgId, versionId, opts)` takes `{ strict: true }`: the three failure branches (grid upsert, version upsert, structure save) then rethrow after logging instead of swallowing. Only `cgAutoSave(true)` uses it (via `cgCreateNewVersionDirect`, which must not copy server data older than the editor, and via `cgCloneGrid`'s flush of the open source version); every other caller keeps the log-and-continue behaviour. `?v=22`.

## No create fallback on a cost-grid upsert (2026-10-16, proposal-clone-followups cycle)

`_cgUpsertVersionToApi` used to retry a failed grid or version `PATCH` as a `POST`. Grid and version ids are always server-assigned, so both already exist when it runs. The retry either created a duplicate (`POST /api/cost-grids` ignores a client id; a version `POST` succeeds on an all-Draft grid) or failed with an error that replaced the `PATCH`'s real cause — on a published grid, the version-creation rule's message (B-004). A failed `PATCH` is now logged and, under `{ strict: true }`, rethrown — never followed by a `POST`. `_pushProjectToApiDetailed` keeps its update-then-create fallback (section above). Covered by `js/lib/api-sync-upsert.test.js`. `?v=23`.

## A failed name save no longer stops the version save; STRUCTURE_RULE is shown (2026-10-23, hardening-costgrid cycle)

Spec `docs/superpowers/specs/2026-10-23-hardening-costgrid-design.md`, report `docs/superpowers/reports/2026-10-24-hardening-costgrid-finish-cycle.md`. In `_cgUpsertVersionToApi` a failed grid-name `PATCH` no longer returns before the version and structure writes: they still run, and the call resolves `false` (B-088). Under `{ strict: true }` the name failure still throws first. A structure `PUT` refused with `code: 'STRUCTURE_RULE'` (a task linked to a project is missing from the draft, see [docs/api/lib.md](../api/lib.md) → `structure-rules.js`) is refused again on every autosave, so `showInfo` tells the user once per version (`_cgRuleNotified`, shared with `DATE_RULE`) that the changes are not being saved and to reload; the Set is never cleared — accepted follow-up. Covered by `js/lib/api-sync-upsert.test.js`.

## DATE_RULE: the structure is still saved, the PATCH retried once (2026-10-26, dates C3)

Spec `docs/superpowers/specs/2026-10-26-dates-c3-task-period-design.md`, report `docs/superpowers/reports/2026-10-26-dates-c3-task-period-finish-cycle.md`. The server checks a version `PATCH` against the STORED tasks and a structure `PUT` against the STORED period, so a save that moves a task inward and shrinks the period is refused by each leg alone. `_cgUpsertVersionToApi` therefore keeps a `DATE_RULE` refusal of the version `PATCH` aside, still saves the structure, and retries the `PATCH` once, only when that structure `PUT` ran and succeeded; a refused `PATCH` is never retried as a `POST`. When the retry is not possible the refusal is shown (once per version, `_cgRuleNotified`). The notice for a `DATE_RULE` refusal ends "Your changes to this version are not being saved until this is fixed."; the `STRUCTURE_RULE` notice keeps its "reload the page" wording. The project-config equivalent is an open follow-up (B-150 in `docs/BACKLOG.md`). Covered by `js/lib/api-sync-upsert.test.js`. `?v=27`.

## The period travels with the tasks (2026-10-28, dates C4)

Spec `docs/superpowers/specs/2026-10-26-dates-c4-saves-after-period-rule-design.md`, report `docs/superpowers/reports/2026-10-28-dates-c4-saves-period-finish-cycle.md`. Supersedes the C3 retry above.
- **Cost grid.** With the structure loaded, `_cgUpsertVersionToApi` sends the version `PATCH` without `startDate`/`endDate` and the structure `PUT` with `period: { startDate, endDate }` (`''` clears a side), so a move, shrink or shift of the period together with the tasks is one checked write. Without a loaded structure the `PATCH` still carries the period. The `PATCH` retry is gone; a refused `PATCH` no longer stops the structure save. The strict flush (`+ New version`, Clone) saves the structure with the new period before the copy.
- **Notices.** `_cgRuleNotified` is keyed `<versionId>|<code>|<message>`; `_cgForgetRuleNotices(versionId)` clears a version's keys after a successful structure save and after `cgLoadStructureFromApi`. A structure `DATE_RULE` notice ends "Tasks and the period of this version are not saved until this is fixed; other changes are saved."; a `PATCH` `DATE_RULE` notice keeps the C3 sentence "Your changes to this version are not being saved until this is fixed.", because a refused `PATCH` saves nothing (a deviation from the Spec's §3.1, which had one sentence for both). The Spec's "Task dates and the period …" became "Tasks and the period …" at Gate 3: a refused structure drops every task edit, not only its dates.
- **Project.** `_pushProjectToApiDetailed` drops the period from the project `PATCH` when the tasks are sent and calls `Api.projects.saveTasks(id, { tasks, period })`; a tasks failure is recorded as `{ part: 'tasks', withPeriod: true }`. The `POST` fallback keeps the full body. `_pushProjectToApi` has no production caller left: both `js/costgrid.js` callers use `_pushProjectToApiDetailed`.

Covered by `js/lib/api-sync-upsert.test.js`, `js/lib/api-sync-push-project.test.js`. `?v=28`.

## The version rate is the server's (2026-10-29, B-176)

Spec `docs/superpowers/specs/2026-10-29-pot-reference-version-and-version-rate-design.md`. `_cgUpsertVersionToApi`'s version `PATCH` no longer sends `currencyRate`: the server decides the rate from `currency` (`docs/api/lib.md` → `version-rate.js`). A `CURRENCY_RULE` refusal of that `PATCH` is notified once, like `DATE_RULE` ("… is not active. Your changes to this version are not being saved until this is fixed."), and never retried as a `POST`; `notifyRefusal`'s "reload the page" tail is now keyed on `STRUCTURE_RULE`. Covered by `js/lib/api-sync-upsert.test.js`. `?v=29`.
