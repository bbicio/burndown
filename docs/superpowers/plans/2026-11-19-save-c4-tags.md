# Contratto di salvataggio, ciclo 4: tag di versioni e progetti — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Spuntare o togliere un tag scrive solo quel tag. Una lettura fallita blocca le modifiche invece di valere "nessun tag". Una scrittura fallita si vede e torna allo stato del server.

**Architecture:**
- **Server:** due coppie di route puntuali (`PUT`/`DELETE …/tags/:itemId`) sostituiscono le due `PUT …/tags` di sostituzione completa e rispondono con la lista intera.
- **Client:** il modulo puro `js/lib/tag-toggle.js` sceglie il verbo e passa per `apiSave`, che accetta un `{ background }` facoltativo. project-config e costgrid tengono uno stato `tagsState` (`loading`/`ok`/`unknown`) e adottano la lista del server.

**Tech Stack:** Node 24, Express, `pg`; Vue 3 da CDN, vitest 4 + jsdom; PostgreSQL 16.

**Spec:** `docs/superpowers/specs/2026-11-19-save-c4-tags-design.md`
**Branch:** `save-c4-tags`
**Risk class:** high-risk — file condivisi caricati da più pagine (`js/api.js`, `js/lib/save.js`); permessi sulle route nuove (`canEdit`)

**Task indipendenti:** in parte.

- Task 1 (server) e Task 2 (`apiSave` + `tag-toggle.js`) sono indipendenti tra loro.
- Task 3 (project-config) e Task 4 (costgrid) consumano entrambi l'interfaccia del Task 2 e le route del Task 1, e sono indipendenti tra loro.
- Tra la fine del Task 1 e quella dei Task 3-4 le pagine del branch chiamano route che non esistono più. Il branch si integra solo alla fine, con `/finish-cycle`.

## Global Constraints

- **Route progetto:** `PUT /api/projects/:id/tags/:itemId` e `DELETE /api/projects/:id/tags/:itemId` → `200` con la lista di `GET /api/projects/:id/tags` (stessa forma `{ item_id, label, status, list_id, list_name, list_slug }`, stesso `ORDER BY al.name, ali.label`).
- **Route versione:** `PUT`/`DELETE /api/cost-grids/:id/versions/:vId/tags/:itemId` → `200` con la lista di `GET …/versions/:vId/tags`.
- **Ordine degli errori, progetto:** `canEdit` falso → `403 { error: 'Access denied' }`; progetto assente → `404 { error: 'Project not found' }`; `itemId` non UUID → `400 { error: 'itemId must be a valid UUID' }`; item inesistente (`23503`) → `400 { error: 'Tag item does not exist' }`.
- **Ordine degli errori, versione:** `canEdit` falso → 403 `Access denied`; versione non della grid → `404 { error: 'Version not found' }`; `locked` → `400 { error: 'Version is locked' }`; poi UUID e item come sopra.
- **Idempotenza:** assegnare un tag già assegnato o togliere un tag assente → 200 con la lista.
- **`enqueueProjectCode(projectId)`** parte solo quando l'`INSERT` o la `DELETE` toccano una riga (`rowCount > 0`).
- **Qualunque item esistente è accettato, anche se inattivo.**
- **`apiSave(method, path, body, opts)`:** `opts?.background === true` → `apiFetch(path, { method, body, background: true })`; senza `opts` la chiamata ad `apiFetch` è identica a oggi.
- **Testi utente (inglese, esatti):** `Tags could not be loaded.`, pulsante `Retry`, sommario chiuso `Unavailable`.
- **`?v=N`:** bump di ogni file versionato modificato in **ogni** pagina che lo carica (`grep -rn 'js/api.js?v=' *.html`, e così per gli altri); `js/lib/tag-toggle.js` entra con `?v=1`.
- **Ogni task aggiorna i documenti della sua riga `**Docs:**` nello stesso commit.**
- **Prima di ogni `scripts/run-tests.sh`** (circa 6 minuti): `node --check` dei file JS toccati e i test backend in `api/`, concatenati con `&&`; nel log va cercato `Unexpected error`. Il worktree ha bisogno del `.env` copiato dal checkout principale.

## Review Focus

1. **Cambio versione durante una scrittura in costgrid:** il risultato (righe o messaggio) arriva quando `verId` è già cambiato e non va dipinto sull'altra versione. Lo pinna il test sorgente del Task 4 sulla guardia `verId`, più HD-04 a mano.
2. **Tag disattivato assegnato:** un `DELETE` su un item `inactive` risponde 200 e la riga sparisce (`test-api.js`, Task 1).
3. **Rimozione già fatta in un'altra scheda:** il `DELETE` di un tag assente risponde 200 con la lista, e la pagina la adotta (`test-api.js`, Task 1; vitest, Task 2).
4. **Viewer che bypassa l'interfaccia:** un viewer che chiama le route riceve 403 (`test-api.js`, Task 1).
5. **Retry durante una scrittura:** Retry è disabilitato mentre `tagSaving` è vero, e una lettura fallita non svuota mai le righe (test sorgente dei Task 3-4).

## Decisioni aperte

1. **Risk class `high-risk` invece di `standard` (Brief e Spec).** Alternativa scartata: `standard`. Perché: §6.1b mette in `high-risk` i file condivisi caricati da più pagine, e il ciclo modifica `js/api.js` e `js/lib/save.js`; la riga della Spec è allineata.
2. **La rimozione delle route di sostituzione completa sta nel Task 1, prima che le pagine passino alle route nuove (Task 3-4).** Alternativa scartata: un task finale di rimozione. Perché: i test `TAG-*` di quelle route si riscrivono comunque nel Task 1, e il branch si integra solo alla fine.
3. **Le pagine si verificano con test sorgente (`js/lib/tag-pages.test.js`) e con il Gate 2 a mano; la logica dei fallimenti si verifica con vitest su `tag-toggle.js`.** Alternativa scartata: montare le pagine Vue in jsdom. Perché: nessun test del progetto monta queste pagine, e la parte decisionale sta nel modulo puro.
