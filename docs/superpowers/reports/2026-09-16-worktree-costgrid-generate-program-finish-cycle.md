# Finish-cycle report — worktree-costgrid-generate-program

**Date:** 2026-09-16
**Branch:** worktree-costgrid-generate-program → main

## What was done

8 commits:

1. `feat: auto-create/link a Program when generating a partial-task project` — when generating a project from a partial task selection on a proposal (any pipeline stage except Draft) with no program established yet, a "Create Program" modal (name + code) is required before generation completes; canceling aborts the whole generation. Once established, any later generation from the same proposal auto-links to that program.
2. `fix: replace native prompt(), center Create Program modal, fix broken post-generate dialog` — three user-reported bugs from manual testing: the project-name entry moved from a native `prompt()` to a real HTML modal (`#cgProjectNameModal`); the Create Program modal was recentered (`modal-dialog-centered modal-sm`); the post-generation "open configuration?" confirm dialog's Confirm button (previously calling a dead `openConfigModal()` reference) now actually navigates to `project-config.html`.
3. `fix: convert Add-to-project confirmation to a real Bootstrap modal` — the "Add task to existing project" flow used a transparent, non-modal `confirm()`-style dialog with a z-index/layering bug; replaced with a real Bootstrap modal (`#cgAddToProjectModal`), and the project dropdown now resets between uses instead of retaining the previous selection.
4. `feat: add optional project code field to the Generate project modal` — the project-name modal gained an optional "Project code" text field.
5. `fix: code review round-1 findings for costgrid program auto-link` — relaxed `POST /api/programs` to `requireAuth` (was `requireAdmin`, which would 403 a non-admin proposal owner/editor); made the project-push + linked-project-sync API calls awaited instead of fire-and-forget so the post-generation dialog can't offer to navigate before the project is actually persisted; rewrote `findExistingProgramForProposal` to mirror `pipeline.html`'s stale-ID resolution pattern (direct match → scoped name match → single-project-in-scope fallback), with 3 new unit tests; removed a stale free-task-id snapshot in favor of recomputing free tasks fresh at confirm time.
6. `fix: code review round-2 findings for costgrid program auto-link` — 11 findings: closed a double-submit window round-1's own fix had opened (selection-mode exit moved before the awaited calls); `_pushProjectToApi` now returns a success boolean so a failed core upsert shows a sync-failure warning instead of a false "success" dialog; fixed a pre-existing, unrelated ownership hole in `POST /programs/:id/share` (any authenticated user could grant themselves editor on every project in an arbitrary program); relaxed `PATCH /programs/:id` to `requireAuth` with the same ownership check; added a "link to an existing program" option to the Create Program modal; aligned the free-task computation with the established dual id+name convention; chained modal-to-modal transitions off `hidden.bs.modal` instead of firing synchronously after `.hide()`; attached `.catch()` at all 3 call sites of the now-`async` `cgDoGenerateProject`; replaced remaining native `alert()`s on these flows with `showInfo()`; minor UI polish (stale validation errors, a duplicate Vue `:key`).
7. `fix: code review round-3 findings for costgrid program auto-link` — 3 Important findings: the round-2 "link to existing program" dropdown never actually rendered (`getPrograms()` is a classic-script global unresolvable from inside a compiled Vue template — the same landmine already documented twice elsewhere in this codebase), fixed with a reactive `programs` array; round-2's own `hideModalThen` fix had reopened a double-submit window in `submitProjectNameModal` (no in-flight guard), closed with a `submitting` flag; `js/api-sync.js`'s cache-bust wasn't bumped despite round 2 changing its `_pushProjectToApi` return value, which would have shown a false "sync failed" warning on every successful generation for any browser with the old file cached — bumped `?v=14` → `?v=15` across all 5 pages that load it.
8. `fix: keep local programs cache in sync after creating a new program` — companion fix so a freshly created program appears in the existing-program dropdown for a retry within the same page session.

**Manual verification:** all bug-fix rounds verified in the isolated `scripts/test-branch.sh` environment, including finding 1's non-admin permission fix — tested end-to-end via `curl` as a genuine `role='user'` account (`POST /api/programs` → 201, not 403), after browser-automation attempts to drive the same flow repeatedly hit this session's known recurring renderer-freeze glitch.

## Code review follow-ups

Three rounds of code review ran (finish-cycle's Gate 3 cap). All Important findings across all three rounds were fixed in-cycle. The following Minor findings from round 3 were explicitly accepted as follow-ups (user decision: fix the 3 Important findings, defer the Minors, skip a 4th review round):

- **Round 3 — `confirmAddToProject` has the same unguarded-double-click shape** (`costgrid.html`, `confirmAddToProject()`) as the `submitProjectNameModal` bug fixed in commit 7 — `.hide()` then `await cgDoAddTasksToProject(...)` with no in-flight guard; a second click during the modal fade could append the same tasks twice. Narrower window than the fixed bug, same fix pattern (a `submitting`-style flag) would apply.
- **Round 3 — `PATCH /programs/:id` relaxed to `requireAuth` with no actual non-admin caller in the repo yet** (`api/src/routes/config.js`) — the only current caller is `config.html`, which is itself admin-only, so the "let a non-admin fix a typo right after creating it" scenario the relaxation was justified by has no live UI path today. Combined with the zero-projects ownership-check carve-out, any authenticated user can currently rename any program that has no projects yet. Worth either tightening the carve-out (e.g. record and check a creator/owner) or reverting to `requireAdmin` until a real non-admin caller exists.
- **Round 3 — `cgGenerateProject()`'s free-task check is still id-only** (`js/costgrid.js:1024-1025`), and so are `selectAllFree()`/`selectAllFreeInPhase()` (`costgrid.html`) — round 2 only fixed the dual id+name check for `cgSubmitProjectName`'s decision of whether to prompt for a program; these three earlier-stage checks (which tasks are offered/selectable as "free" in the first place) still match by id alone, so a task assigned under a stale id but matched by name can still be offered and duplicated into a new project.
- **Round 3 — a failed project push still leaves local `linkedProjects`/autosave state pointing at a non-existent server-side project** (`js/costgrid.js`, `cgDoGenerateProject`) — self-heals on reload since the server is authoritative, and the shown warning tells the user to reload, but the local state mutation isn't actually skipped on failure, just the success dialog is.
- **Round 3 — no integration-test coverage for the two new ownership/permission checks** (`POST /programs/:id/share`'s new 403 path, `PATCH /programs/:id`'s new 403 path) — `test-api.js`'s `testPrograms()` only covers `POST /programs` (PRG-01..04); the suite has no non-admin test account, a gap the added comment already acknowledges. The security-relevant half of round 2's fixes is manual-verification-only for now.

Also noted, not treated as a defect: round 2 flagged that the new "Project code" field has no uniqueness check — investigated and confirmed this matches pre-existing, already-accepted behavior across the whole codebase (`projects.code` has no DB uniqueness constraint anywhere; CLAUDE.md documents this as accepted for timesheets/actuals resolution too), not a new problem introduced by this branch. No fix applied, by design.
