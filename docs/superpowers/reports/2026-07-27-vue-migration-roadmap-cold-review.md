## Goal achievement

The roadmap's stated goal — get every page onto Vue 3 (CDN, no build step) except the 9-line `index.html` redirect — is complete. Verified fresh (not from memory): `grep -L "Vue.createApp\|vue@3\|vue.global" *.html` confirms only `index.html` lacks a Vue signature. All 7 migrated pages (`terms.html`, `_db-reset.html`, `project-config.html`, `portfolio.html`, `pipeline.html`, `costgrid.html`, `planning.html`) follow the same single-`Vue.createApp({...}).mount(...)` pattern, no sub-components, no build step — the pattern held consistently across 8 cycles and roughly two weeks without drifting into per-page bespoke architectures.

Each cycle's own manual verification + code review gate caught real, cycle-specific regressions before merge (detailed per-cycle in each report). Reading all 8 with fresh eyes, the pattern of defects is consistent and already well-understood by this project: bare global references in template expressions, reactive `:value` bindings fighting in-progress user input, and computed properties reading non-reactive globals instead of Vue-tracked state. Every instance found was fixed before merge; none escaped to `main` unaddressed.

## Systemic observations (visible only from the whole-picture view)

1. **`js/costgrid.js`'s deferred "eventual fate" decision is now ripe.** The `costgrid.html` cycle explicitly deferred this "until `planning.html` (the last Vanilla consumer) is migrated" — that just happened. Verified fresh: `grep -l "js/costgrid.js" *.html` now returns only `pipeline.html` and `costgrid.html` (down from 3 pages before this cycle). `costgrid.html` already only touches it through the bridge pattern (`_cgVueApp` delegation); `pipeline.html` is the sole remaining page calling its ~15 kept-unchanged functions directly as globals (`cgConfirmDeleteGrid`, `cgConfirmDeleteVersion`, `cgCloneGrid`, `cgGenerateProject`, etc., per `CLAUDE.md`'s own `js/costgrid.js` entry). This is now a two-consumer problem, not a five-consumer one — genuinely worth a deliberate decision (keep as permanent shared Vanilla service layer vs. eventually fold into `pipeline.html`'s own Vue instance) rather than another cycle's implicit deferral.

2. **The empirical jsdom + real `vue.global.js` mount test, adopted starting with the `portfolio.html` cycle, was the single highest-value process change in this roadmap.** Its own report is explicit: 3 severe Critical bugs (a fatal `v-html`-with-fallback-content compile error that would have aborted every single page load; multiple bare-global template references that resolve to `undefined` in Vue 3's compiled-template mode; a stale-closure bug from re-exporting a reassigned module binding) were invisible to 8 independent finder-agent passes, every task-level review, and `npm test`'s vitest suite — and were only caught because that cycle was the first to actually mount the app. Every subsequent Tier 2 cycle (`pipeline.html`, `costgrid.html`, `planning.html`) adopted this as a standard final task in their own design specs, which is good — but it lives only as a repeated per-plan convention, not as a named, permanent step in `docs/superpowers/PROCESS.md` itself. Since no Vue-migration cycles remain on this roadmap, the value of formalizing it in `PROCESS.md` is now specifically for the *next* time this project builds a from-scratch Vue page (a new feature, not a migration) — worth a deliberate decision on whether the empirical-mount-test step generalizes beyond "migration cycles" to "any cycle introducing new Vue template markup."

3. **Three fully-orphaned files accumulated across the roadmap and were never cleaned up in the cycle that orphaned them** (`js/dashboard.js` since the `portfolio.html` cycle, `js/config-form.js` as of this very cycle, `js/main.js` pre-dating the roadmap). This project's own established convention is "don't delete unused files during migrations" — a deliberate choice to keep migration diffs minimal and reviewable — but the accumulation is now three files, all independently confirmed fully unreachable (zero `<script src>` references anywhere in the repo). This is exactly the kind of grouped, low-risk cleanup this roadmap's own precedent (see the `test-branch.sh` cold review's grouped-cycle recommendation) is suited for.

4. **`initNav()`'s no-error-banner-on-auth-failure gap (item 15) is consistent, not a regression** — it was true of the *original* Vanilla `initNav()` pattern too, inherited unchanged by every migrated page. No single cycle treated it as a defect because each only compared its own page's before/after behavior, and it never got worse. Only visible from the roadmap-wide view: this is now the *universal* auth-failure UX across all 9 authenticated pages, not a one-off. Worth a decision on whether this is acceptable permanently, independent of any further Vue migration work (this is a `js/nav.js` change, touching every page at once — a different risk profile than a single-page migration).

5. **No cross-page regression was found in this review.** Each of the 5 Tier 2 pages shares `js/roles.js`/`js/clients.js`/`js/programs.js` (`js/ratecards.js` also on `costgrid.html`) as globals — verified fresh that all 5 still load these scripts and none broke a sibling page's usage (`getClientName()`, `loadRolesFromApi()`, etc. remain called consistently). The roadmap's own precedent of manual cross-page smoke-testing after every Tier 2 cycle (explicitly called out in each design spec's "Backward compatibility" section) appears to have worked as intended.

## Recommendation

None of the open items above block current, verified-working usage — the roadmap's core goal is done and the app is in a good resting state. If a follow-up consolidation effort is picked up, group by shared concern rather than one-cycle-per-item:

- **Cycle A — Dead-file cleanup**: items 7, 8, 9, 11 (`js/dashboard.js`, `js/config-form.js`, `js/main.js`, `openPlanningAiAnalysis()`). All four are independently confirmed fully unreachable right now — this is the lowest-risk, highest-confidence cleanup available, and the natural moment to do it now that the roadmap that orphaned two of these files is closed.
- **Cycle B — `js/costgrid.js` fate decision**: item 12, informed by items 13-14 (its two still-open PLAUSIBLE findings). Now that it's down to 2 consumers, decide deliberately: keep as a permanent shared Vanilla service layer (document it as such, stop treating it as "to be migrated eventually"), or fold it into `pipeline.html`'s own Vue instance and drop the bridge pattern from `costgrid.html` entirely.
- **Cycle C — Cost-grid/pipeline product decisions**: items 1, 4, 5, 6 (New Proposal flow, delete-only-version UX, single-version tab label, Publish validation message) — these are product/UX questions, not migration bugs, better suited to a product-decision conversation than a code cycle by itself.
- **Cycle D — Known display bugs**: items 2, 3 (phasing panel rounding, Export XLS ExcelJS missing) — both already explicitly deferred by the user in their originating cycles; grouping them together avoids two near-identical small cycles.
- **Documentation-only, no cycle needed**: item 16 (static-file bind-mount staleness note) — a single `CLAUDE.md` sentence, not worth its own cycle; can be folded into whichever cycle next touches `CLAUDE.md`'s Development section.

Decision as of 2026-07-27: **left in the general backlog, no cycle opened now.** Revisit if/when any of these items starts causing real friction (especially item 1, "New Proposal," if it resurfaces with a reproducible case), or as a deliberate consolidation pass.
