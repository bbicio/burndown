# api/src/lib/

Pure functions extracted for unit testing (`node:test`, run via `npm test`/`node --test` from `api/`), mirroring the frontend's `js/lib/` convention.

This file holds the full function-by-function reference and implementation narrative for `api/src/lib/` — signatures, what each function does, cycle-by-cycle bug history, and which routes consume which module. `CLAUDE.md`'s File structure entry keeps only a one-line pointer; when working on any `api/src/lib/*.js` file, read this file, not that line, for the detail. See `/sync-docs`'s routing rule for where future changes to these modules should be written.

## date-parse.js

`parseFlexibleDate(a, b, year)`: disambiguates day/month order deterministically when one value is >12 (unambiguous), falls back to MM/DD (the source export's known convention) only when genuinely ambiguous (both ≤12), validates against real calendar/leap-year arithmetic, throws on an invalid date. Consumed by `docs/api/timesheets.md`'s `formatDate()`, which now rejects the entire upload (400, no partial DB writes) if any row's date can't be resolved — either a calendar-invalid D/M/YYYY date (via `parseFlexibleDate`) or a cell value that doesn't match any recognized date format at all (2026-08; previously fell through to storing the raw, un-validated string as the entry's date). A whitespace-only cell is treated as "no date" (`null`), not an error.

`trimRowKeys(row)` trims every uploaded row's object keys before `resolveColumnMap()` reads them (predates this session), so header/value whitespace mismatches between the sampled header row and individual data rows can't cause a column-mapping miss.

### resolveColumnMap(headers) — `api/src/routes/timesheets.js`

Column-header-to-field resolver for the XLS upload, exported (like `formatDate`) for direct `node:test` coverage. Resolves each of `colDate/colRole/colOwner/colHours/colTask/colNotes/colProjId/colProjName` via a **specificity-scored global assignment** (2026-08, replacing the earlier fixed-declaration-order/first-match algorithm) — an audit (`docs/superpowers/audits/2026-08-05-timesheet-column-mapping-ambiguity-audit.md`) found the old algorithm could silently misassign a column whenever a generic keyword from an early-declared field (e.g. `colOwner`'s bare `'name'`/`'nome'`) collided with a more specific keyword belonging to a later-declared field (e.g. `colProjName`'s `'project name'`) — the outcome depended purely on which column happened to appear first in the uploaded file, with no error ever raised (`"Project Name"` could end up as the `owner` value for every row, `colProjName` left `null`).

Every (header, field) match is now scored — tier 2 if the header equals the keyword exactly, tier 1 if the keyword appears as a whole word inside the header (word-boundary aware via a manual `\p{L}\p{N}` Unicode-property check, not a plain regex `\b`, since `\b` doesn't treat accented letters like the `à` in `attività` as word characters and would misfire on that candidate); within a tier, a longer/more specific keyword outranks a shorter/generic one — then all matches across every header and every field are sorted by score and assigned greedily (highest-specificity first), so field-declaration order only decides genuine ties (e.g. `"Resource Name"` still resolves to `colRole`, not `colOwner`, because `'resource'` (8 chars) always outscores `'name'` (4 chars) — it never reaches the tie-break).

`colTask`'s candidate list gained `'task name'`/`'nome attività'` (mirroring `colProjName`'s existing `'project name'` pattern) — a gap found mid-fix: the bare `'task'` (4 chars) tied exactly with `colOwner`'s bare `'name'` (4 chars) for the header `"Task Name"`, and without a more specific candidate to break that tie cleanly, declaration order silently regressed the exact bug being fixed.

2026-08 hardening: `matchSpecificity()` now scans every occurrence of a candidate substring, not just the first — previously a candidate whose first occurrence wasn't word-boundary-clean returned no match at all, even if a later occurrence in the same header was; and `resolveColumnMap()`'s `usedHeaders` collision-tracking `Set` now stores column index (`m.headerIdx`) instead of header text (`m.header`), so the string-vs-index distinction doesn't conflate two distinct columns that happen to share identical header text — though the practical benefit is bounded by `result[field]` still storing the header *string* (dereferenced by callers via `row[map.colX]`), so two identically-named columns still resolve to the same underlying value; no two fields in the current `FIELD_CANDIDATES` table share an overlapping candidate word, so a genuine cross-field collision isn't constructible from today's real candidate list.

The non-optimal greedy (rather than globally-optimal bipartite) assignment strategy is unchanged — no demonstrated real-world trigger, left as documented backlog.

## sold-hours.js

`isValidSoldHours(value)`/`SOLD_HOURS_FRACTIONS` (`[0, 0.25, 0.5, 0.75]`): validates that a sold-hours value lands on a quarter-hour boundary. Consumed by `cost-grids.js` and `projects.js` for their own sold-hours validation.

## email-template.js

`renderEmailHtml({ bodyHtml, appUrl, year })`: the shared HTML wrapper (navy/magenta logo header, footer with app URL + year) used by every system email (invite, password reset, share notification, export ready, admin notification) — mirrors `login.html`'s own logo styling so emails match the product's visual identity.

## rate-resolve.js (2026-09)

`resolveFee(tasks, taskName, role)`: backend port of `js/core.js`'s `findRate()` (case-insensitive task+role match, fallback to a matched task's first resource, `0` — never `null` — when nothing matches). Consumed by `docs/api/timesheets.md`'s `POST /upload` to snapshot a `fee` value onto every uploaded timesheet entry at insert time; the `0` fallback (vs. `findRate`'s `null`) is deliberate — the value is persisted, not display-only, so it needs a concrete number, and `0` matches the same "no data" display convention already used for Fee/Spent throughout `timesheets.html`.

## is-admin.js (2026-09)

`isAdminRole(role)`: `role === 'admin' || role === 'sysadmin'`, single source of truth for "does this role carry admin capabilities?" now that `role` is 3-tier. Swept into every route file that had its own bare `role === 'admin'`/`role !== 'admin'` literal instead of going through the shared `requireAdmin` middleware (found by the final whole-branch review of the sysadmin-role cycle, live-verified: a real sysadmin saw 0 projects/grids/timesheets and 403s on reporting/broadcast before this fix) — `cost-grids.js`, `projects.js`, `timesheets.js`, `exports.js`, `reporting.js`, `notifications.js`, `pipeline-years.js`. `node:test`-covered (4 cases).

## role-transition.js

`roleChangeError(actorRole, targetCurrentRole, requestedRole)`: pure validation for a requested `users.role` change, returns `null` (allowed) or an error string. Rules: only a sysadmin may grant/revoke sysadmin, or touch a row that is currently sysadmin at all (in either direction — this covers demotion too, not just promotion); promotion to sysadmin is only valid from a target currently `admin` (no direct `user → sysadmin`); demotion from sysadmin is only valid to `admin` (no direct `sysadmin → user`, added after a code-review finding — the promotion side already had this two-step rule, the demotion side didn't). Consumed by `PATCH /api/users/:id` (`docs/api/lib.md` reference; route itself in `api/src/routes/users.js`). 9 `node:test` cases.

## match-resource.js (2026-09, Cycle 3b)

Pure helpers for linking the free-text `owner` in uploaded actuals to `resources` (DB half: `api/src/services/resource-matching.js`; narrative: `docs/api/resources.md`). `normalizeName(input)`: NFD accent strip, lowercase, non-letter/digit runs → space, tokens **sorted** and joined — so "Rossi, Mario." and "mario rossi" are the same key; `''` for nothing left. `buildMatchContext(resources, aliases)` → `{ aliasByKey, activeByKey, inactiveByKey }` (active resources are tried first, inactive ones are indexed separately as a fallback; an alias with a null `resource_id` means "ignored"). `matchOwner(name, ctx)` → `empty | ignored | alias | matched | ambiguous | unmatched` (alias beats name; two active namesakes are `ambiguous`, never matched; inactive resources are a fallback only when no active one shares the name (one inactive matches, several are `ambiguous`); an alias to an inactive resource still resolves). `aggregateUnmatched(rowsByCode, ctx)` → the (project, name) rows still needing an admin, summing hours per normalized name and rounding to 2 decimals so 0.1 + 0.2 reads 0.3. 16 `node:test` cases.

## slugify.js (2026-09)

`slugify(name)`: lowercase, ASCII-only, hyphen-separated slug (Unicode NFD-normalizes and strips combining diacritics before collapsing non-alphanumerics to `-`), or `''` for input with no alphanumeric characters at all. Called exactly once per `attribute_lists` row, at `POST /api/attribute-lists` creation time (`api/src/routes/attribute-lists.js`) — the result is stored and never regenerated, so this function's output for a given input must never change once anything relies on it. The Unicode-range regex literal must stay written as the `̀-ͯ` escape-sequence text, not embedded combining-mark glyphs (a final-review finding on the introducing cycle found the source briefly contained the latter — invisible characters an editor/formatter/copy-paste could silently mangle). 7 `node:test` cases.

## resource-profile.js (2026-09-25, Cycle 3c)

Pure profile builders, no DB (DB half: `api/src/services/profile-engine.js`; narrative: `docs/api/profile-engine.md`). `monthOf(date)`: `'YYYY-MM-DD...'` to `'YYYY-MM'` (month 01-12) else `null`. `normalizeTask(task)`: trimmed, whitespace-collapsed name; key is the lowercased name; empty becomes `'(no task)'`. `buildContributions(rows, ctx, projectName)`: actuals rows of ONE project code to a `Map<resourceId, { projectName, hours, first, last, roles{}, tasks{} }>`; only owners that `matchOwner` resolves to `alias` or `matched` contribute; hours rounded to 2 decimals. `aggregateProfile(contribByCode, projectsByCode, now)`: sums one resource's contributions into the stored profile (`totals`, `dimensions[slug].values` with `untaggedHours`, `roles`, `projects`, each with `projectCodes`). `node:test` cases in `resource-profile.test.js`.

## job-schedule.js (2026-09-25, Cycle 3c)

`parseJobSettings(rows)`: `app_settings` rows to `{ enabled, intervalMin }`; the interval must be an integer 1-1440, else the default 10; `enabled` is true for **any value other than** `'false'` (case-insensitive, trimmed). `isJobDue(settings, lastRunStartedAt, now)`: a disabled job is never due, a job that never ran always is, otherwise due once `intervalMin` minutes have passed since the last run START. `node:test` cases in `job-schedule.test.js`.

**Cycle 3d (2026-09-28) additions**, for the profile jobs console (`docs/pages/profile-jobs.md`): `composeRunError(errors)` (joins with "; ", caps at 500 chars, `null` when empty — the single composition shared by `recordRun` and the throttle below). `shouldRecordRun({ trigger, projects, errors, lastRunError })`: manual runs are always recorded; a scheduled/bootstrap run is recorded only if it processed something, or failed with an error different from the last recorded run (throttles a permanently-failing code from writing a history row every interval). `nextRunInfo(settings, lastRunStartedAt, now)`: the console's "next run" estimate — disabled → `paused`; never run or an invalid/overdue timestamp → `due`; otherwise `scheduled` at last run + interval; agrees with `isJobDue` at the due/not-due boundary. `jobSettingsError(body)`: strict JSON-type validation for `PUT /api/profile-jobs/settings` (real boolean, integer 1-1440, no numeric/boolean strings, no floats). `deriveProjectStatus(row)`: `'error'` (`last_error` set) > `'queued'` (`queued_at` set) > `'updated'` (`last_processed_at` set) > `'unprocessed'`.


## topic-extract.js (2026-09-29, profile descriptions cycle)

Pure rules of the topic feature, no DB, no network (DB/LLM half: `api/src/services/topic-extraction.js`; narrative: `docs/api/profile-engine.md` and `docs/api/topics.md`). `normalizeTopicName`/`cleanTopicName`/`taskKey` (same key as the actuals task key), `hashText` (SHA-256 of the trimmed text), `isExtractable` (`MIN_TEXT_CHARS = 20`), `descriptionsSignature(tasks)` (order-independent fingerprint used to detect a changed task description), `buildItems(projectDescription, tasks)` (project text plus one item per distinct task name), `buildVocabulary(topicRows, listRows)`, `buildPrompt` / `parseExtraction` (the LLM contract; malformed JSON throws), `finalTopic(id, topicsById)` (follows `merged_into`, bounded, null on a loop), `resolveCandidates(candidates, vocab)` (discards list-value equivalents, over-long names, rejected targets and duplicates; reuses by id or normalised name; at most 5), `resolveProfileTopics(entries, topicsById)` (read-time resolution: approved only, merged followed, project codes unioned) and `topicNameError(name, vocab)` (admin input validation). `node:test` cases in `topic-extract.test.js`; `resource-profile.test.js` gained cases for `aggregateProfile`'s `topics` output (project topics to every contributor, task topics via the task key).

## money-format.js (2026-10-01, money centralization cycle)

`formatMoney(amount, { code, symbol, locale } = {}, { rounded } = {})` — the server twin of `js/lib/money.js`'s `formatMoney` (CommonJS, no build step so the browser module cannot be required): same output for the same inputs (`€ 12.345,00`, `$ 12,345.00`, `¥ 12,346`; `useGrouping: 'always'`; digits from `Intl`, `rounded` drops decimals; missing `code`/`symbol`/`locale` fall back to EUR/`€`/`it-IT`; non-finite amount → zero; never throws on a non-ISO code). Consumed by `api/src/routes/cost-grids.js`'s `notifyAdminsPipelineChange` (the in-app notification admins get when a version's pipeline stage changes — its query now also selects `cu.locale`): `Value: € 21.555` (rounded) instead of the former `symbol + toLocaleString('en-US')`. The two test tables (`money-format.test.js` and `js/lib/money.test.js`) are kept in sync by hand.

## project-rules.js, version-lock.js (2026-10-01, project currency lock cycle)

`project-rules.js` — pure rules that keep a project and the proposal it was generated from in the same currency by inhibiting every way to create, unlink, delete or re-currency them (spec `docs/superpowers/specs/2026-10-01-project-currency-lock-design.md`). Each function returns an error message or `null`; `role` is the **live** DB role (`liveRole` in `middleware/auth.js`), a sysadmin always passes; refusals are `400 { error, code: 'PROJECT_RULE' }` (`RULE_CODE`). `projectCreateError({ role, versionId })` (no proposal while `DIRECT_PROJECT_CREATION_ENABLED` is false), `projectCurrencyChangeError` (any change of the stored currency; an identical value or a missing/empty one = `EUR` passes), `projectLinkChangeError` (clearing the link or pointing it at another version; linking an unlinked project and a re-sent identical id pass, ids compared case-insensitively), `linkCurrencyError` (a project and its version must share the currency at link time), `versionCurrencyChangeError` (only a version that has projects is protected), `projectRemovalError`/`linkRemovalError` and `versionRemovalError({ hasProjects })` (while `PROJECT_REMOVAL_ENABLED` is false). `MESSAGES` holds the approved texts. The two flags (both `false`) are the single switch-back points on the server; `js/lib/project-rules.js` is the browser twin.

Wiring: `routes/projects.js` — `POST /` (rule, then for a `cgVersionId` the version must exist, `Proposal version not found` otherwise, and share the currency), `PATCH /:id` (currency change, link change, new-link check; stored values read before the update, the new-link check repeated inside the transaction under the version lock), `DELETE /:id`; `routes/cost-grids.js` — `PATCH …/versions/:vId` (currency, under the version lock), `DELETE …/versions/:vId` and `DELETE /:id` (`versionHasProjects`/`gridHasProjects`: a `cg_version_projects` row or a `projects.cg_version_id`), `POST …/linked-projects` (currency check + insert under the lock, defensive 404 for a missing version), `DELETE …/linked-projects/:projectId`. A re-sent identical `currency`/`cgVersionId` is accepted (the frontend re-sends the whole project on every save). Tests: `project-rules.test.js` (node:test) and `test-api.js` `PR-01..PR-14`.

`version-lock.js` — `withVersionLock(versionId, fn)` runs `fn(client)` in a transaction holding a transaction-level advisory lock (`pg_advisory_xact_lock(hashtext(<lower-case id>))`), `lockVersion(client, id)` takes it on an open transaction. It serialises, per version, "change the currency of the version" against "link a project to it" (version `PATCH` currency, project `POST` with `cgVersionId`, project `PATCH` null → version, linked-projects `POST`), so the check and the write cannot interleave. Lock order: the version lock is taken before the project row lock (`FOR UPDATE`) in the project `PATCH`. Covered by the concurrency smoke test `PR-14` (a currency change and a link fired together never diverge); the race itself cannot be reproduced on demand, so that test cannot be shown red.
## planning-calendar.js, planning-distribution.js, planning-model.js, planning-request.js (2026-09-29, Planning model cycle)

Pure, DB-free modules behind `POST /api/planning/model` (route: `api/src/routes/planning.js`; DB/cache half: `api/src/services/planning-data.js`; contract, per-view rules and verification: [docs/api/planning-model.md](planning-model.md)). This calculation now exists once: the browser copy in `planning.html` / `js/lib/planning-calc.js` was removed in the same cycle. All are `node:test`-covered (`*.test.js` next to each file).

- `planning-calendar.js`: a "calendar date" is a Date at 00:00 UTC (no server-time-zone dependence). `isoDate(str)` (`YYYY-MM-DD...` to date, `null` for unparsable or impossible dates such as Feb 31), `dateKey`, `addDays`, `mondayOnOrBefore`, `parseTaskDate(str, isEnd)` (`YYYYMMDD`, or legacy `YYYYMM` = first/last day of the month; empty = epoch / year 9999), `getCalendarWeeks(start, end, today)` (Monday-Sunday weeks with `key` = Monday `YYYY-MM-DD`, `monthKey` from the week's Monday, `isPast`, `isCurrent`), `countFutureTaskWeeks` and `makeFutureWeekCounter(today)` (memoised: an undated task ends in year 9999).
- `planning-distribution.js`: `matchesTaskRole` (case-insensitive, null-safe), `computeResidual`, `distributeFutureResidual` (uniform spread, pulse mode), `redistributeExcludingInactive`, `hasValidPhasing`, `taskFutureWeeks` and `phasedSeries` (Phase 2: monthly distribution normalised over all future months of the task, independent of the visible window, By Role only).
- `planning-model.js`: `normalizeActuals`, `groupActualsByProject(projects, sheets)`, `uniqueOwnerNames`, `rolePassesTeams`, `inWeek` (inclusive Sunday, By Owner) and `inWeekLegacy` (Sunday excluded, By Role/By Project: the replicated browser quirk), `roleProjection` / `projectProjection` / `ownerProjection` and the dispatcher `buildProjection(view, input)`. The three projections keep different rules on purpose.
- `planning-request.js`: `parsePlanningRequest(body)` returns `{ ok: true, value }` or `{ ok: false, errors }` (view, id/team list limits, dates, window length, boolean `pulse`).

`match-resource.js` gained `resolveOwnerStatuses(names, resources, aliases)` (moved from `routes/resources.js`): name to `'active' | 'inactive'`, every outcome except an unambiguous match to an inactive resource resolving to `'active'`; consumed by `planning-compute.js` (`POST /api/resources/match-owners` was removed in Cycle B).

## planning-compute.js, team-params.js, team-load.js, team-requirement.js, team-scoring.js, team-ranking.js, assistant-chat.js (2026-09-30, Planning team assistant cycle)

Pure, DB-free modules behind `/api/planning-assistant` (route `api/src/routes/planning-assistant.js`; DB orchestration `api/src/services/planning-assistant.js`; LLM client `api/src/services/llm.js`; contract, formulas and deploy notes: [docs/api/planning-assistant.md](planning-assistant.md)). All are `node:test`-covered (`*.test.js` next to each file).

- `planning-compute.js`: `computePlanningModel(data, visible, req)` is the calculation of `POST /api/planning/model` extracted from the route (filter the requested projects by visibility, build the weeks, resolve owner statuses, `buildProjection`), so the route and the team assistant share one implementation.
- `team-params.js`: `parseParams(input)` validates the flat `params` object (`roles`, `excludeResources`, `requireTags`, `preferTags`, `minFreeHoursPerWeek`, `topN`, `window`, `includeAlternatives`) used by `/rank`, `/chat` and the `rank_team` tool, returning `{ ok, value }` (defaults `topN = 3`, `includeAlternatives = true`) or `{ ok: false, errors }` with one message per field (unknown keys are errors); `resolveExcluded(names, resources)` maps exact full names to resource ids (unknown/ambiguous names are errors).
- `team-load.js`: load and availability from the planning model's `owner` projection: `roleWindow(tasks, project, asOf)` (earliest task start to latest end, project dates as fallback, `null` when undated or already over), `capWindow` (104 weeks max), `loadWindow` (four weeks before the current Monday to the window end), `loadByResource(ownerMap, matchCtx)` (owner names to resources through `matchOwner`; unmatched/ambiguous/ignored names count for nobody), `currentLoad` (mean of the four completed weeks) and `availabilityForWindow` (free hours = max(0, 32 - load) over the non-past weeks: `freeAvg`, `freeMin`).
- `team-requirement.js`: `buildRequirement(...)` turns the target project into what it needs per job title: task names, sold/consumed/needed hours (`computeResidual`), topics (project plus task topics) and the role window.
- `team-scoring.js`: the experience score `scoreResource(profile, role, reqTags, { includeRole })` in 0-100 (role 30 / tag 30 / task 25 / topic 15, saturating exponentials, components that do not apply are dropped) with the evidence behind it; `WEIGHTS`, `SATURATION`, `DIMENSION_WEIGHTS`, `MIN_ALT_SCORE`, `LOW_SCORE` are initial values to tune at Gate 2. `matchedTagHours` is the `requireTags` test.
- `team-ranking.js`: `rankTeam(...)` builds the best / alternative / available tables per role (pool = active, not excluded, `requireTags` satisfied) with a one-line `rationale` per row; `explainResource(...)` returns one person's score breakdown, position and availability. `scoringTags`/`poolPredicate` are shared by both so they always agree.
- `assistant-chat.js`: the conversation layer: `SYSTEM_PROMPT`, the two tool schemas (`rank_team`, `explain_resource`), `buildContextBlock` (project data inside `<project_data>`, `<` escaped), `compactRankResult` (what the model sees of a result) and `runChat` (at most 3 tool rounds, last 20 messages, first message always from the user).
