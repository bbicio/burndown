# /finish-cycle — Development Cycle Closeout Command

Run the full closeout sequence for the current feature branch: a mechanical pre-check of the claims the branch's markdown makes, test, optional manual-verification gate — with `/code-review` launched in the background when that gate *opens*, so it runs while the human verifies — then the code-review gate itself, merge to main, backend restart (if applicable), doc sync, and a persisted report. Every judgment gate (code review findings, merge, the doc-sync/report push) always stops for explicit confirmation. Only objective gates (test pass/fail, pre-flight checks) block or unblock without asking. Since 2026-10-12 the backend restart and the local-branch deletion are **not** judgment gates and no longer ask — Gate 4 steps 7 and 9 say why, PROCESS.md §6b is the rule.

## Pre-flight (automatic, no confirmation)

1. Confirm the current branch is not `main` (`git branch --show-current`). If it is, stop: "finish-cycle must be run from a feature branch, not main."
2. Run `git status --short`. If there is any output (uncommitted changes), stop and ask the user to commit or stash first — do not decide this for them.
3. Run `git log main..HEAD --oneline`. If empty, stop: "No commits to close out on this branch."
4. Determine the branch name (`git branch --show-current`) and sanitize it for filesystem use: replace every `/` with `-`. Store the result as `<branch-sanitized>` — it is used in the Gate 5 report filename.
5. **Informational, non-blocking:** run `git merge-base main HEAD` and `git rev-parse main`. If they differ, run `git rev-list --count <merge-base>..main` and report: "main has advanced N commits since this branch diverged — Gate 4's merge will produce a merge commit, not a fast-forward." Do not block on this.
6. **Timing capture (feeds the Gate 5 report's duration fields).** Record the current wall-clock time (`date '+%Y-%m-%d %H:%M'`) as `<started-at>`, and record it again at every gate boundary from here on — when each of Gates 1-5 is entered, at the moment Gate 4's merge commit is created (`<merged-at>`), and when Gate 5's report is written. Keep the values in the session; nothing is written to disk before Gate 5. These are **elapsed wall-clock** durations and deliberately include time spent waiting for a human answer at a gate — do not try to subtract it, and do not split a gate into "work" and "wait". If a timestamp was genuinely not captured (e.g. `/finish-cycle` was interrupted and resumed in a later session), write `unknown` for that one gate in the report — never reconstruct or estimate it after the fact. Purpose: PROCESS.md §6/§6.6 currently rest on two retrospectively reconstructed anecdotes; these fields are the measured baseline meant to replace them.

## Gate 1 — TEST (blocking, automatic, no confirmation)

0. **Claims pre-check (automatic, no confirmation) — over the `*.md` this branch changed.** Run `git diff main...HEAD -- '*.md'`. If it is empty, say so in one line and go to step 1 — the report's claims pre-check line then says there was nothing to check at this gate, and still carries whatever Gate 3 records. Otherwise, over its added and modified lines, run these four checks and fix what they find, committing the fixes as one `docs:` commit before leaving this gate. It runs *before* `npm test` so the suite — and the documentation guards in it — see the corrected text; this gate still runs the suite exactly once (Gate 5 step 3 runs it again post-merge, on `/sync-docs`'s edits).
   1. **Grep every predicate you touched.** For each sentence asserting something about the repo ("only X does Y", "every Z has W", "no test covers this"), run the grep that would falsify it, over the live repo, and read the hits. Fix the predicate, not the line the sentence sits on.
   2. **Re-measure every number at HEAD** — sizes, counts, margins — against the current tree, never trusting the commit that first wrote the number.
   3. **`git log` every SHA and every adjacency claim.** A cited `<sha>` must exist and be what the sentence says it is; "the next cycle", "the same day", "merged before" are claims about order that `git log` settles.
   4. **Re-check enumerations as a class.** A list of guards, pages, gates or files asserts completeness: regenerate it from the repo (`ls scripts/*-guard.test.js` for the process and documentation guards — **not** the product guards under `js/lib/`, see PROCESS.md §4b; the Pages table for pages; …) and compare the whole list, not the entry you edited.
   - **Re-read your own fixes with the same four checks before committing them.** A fix pass writes new predicates and new numbers, and by the mechanism in PROCESS.md §6.4d that is where the next defect is born; this is the same second pass Gate 3 does per round, owed here too.
   - These four reach mechanical defects only. Judgement prose — whether a rule is right, whether a rationale holds — belongs to Gate 3; do not argue it here.
   - **Ten minutes is a cap, not an estimate.** Check 1 is unbounded in the size of the `.md` diff, and this gate does not stop for a human, so on a large documentation branch it could run far past its budget while blocking everything behind it. At 10 minutes, stop where you are and continue to step 1, recording in the report's **Roadmap notes** that the cap was reached and what was left unchecked. The remainder is Gate 3's problem, which is where it would have been anyway. Reaching the cap is a bounded outcome, not a failure — but a cycle that hit it has partial numbers, and the note is what keeps them from being read as complete.
   - Record what it cost (wall-clock minutes) and what it caught (how many defects, of what kind). Gate 3 adds its own half. This step is an experiment: PROCESS.md §6.4d says what is decided on those numbers, and when.
1. Run `npm test` natively (host Node ≥ 20.12). In a worktree with no `node_modules`, run `npm ci` once first. Use the `docker run ... node:22` one-liner from `CLAUDE.md` only if the host Node is older than 20.12.
   - If it fails: stop immediately, show the failing output verbatim. Do not start Docker. Require a fix and a re-run of `/finish-cycle` from the top.
   - **A red from `scripts/architecture-guard.test.js` is not a code defect** — it means this branch added a route handler, a migration-created table, or an `ALTER TABLE` column that `ARCHITECTURE.md` §5/§6 does not document. The fix is that documentation edit, **on this branch**, before `/finish-cycle` runs again. It is never deferred to Gate 5's `/sync-docs`: that step runs post-merge, which is a gate too late for a check that blocks here. The other documentation guards in this run — `scripts/claude-md-guard.test.js`, `scripts/doc-paths-guard.test.js` and `scripts/decision-ledger-guard.test.js` — say in their own failure messages what they want. That list is not guaranteed complete; `ls scripts/*-guard.test.js` is (PROCESS.md §4b).
2. If it passes, run `git diff --stat main...HEAD` and inspect the listed paths.
   - If any path starts with `api/` (including `api/src/db/migrations/`), or if any touched path's relevance to backend behavior is unclear/ambiguous, proceed to step 3.
   - Otherwise, skip straight to Gate 2.
3. Run `scripts/run-tests.sh`.
   - If it fails: stop immediately, show the failing output verbatim. Require a fix and a re-run of `/finish-cycle` from the top.
4. Proceed automatically to Gate 2 — no confirmation needed, this is an objective gate.

## Gate 2 — MANUAL VERIFICATION (human gate, always confirms)

**Teardown is never your own initiative — every one of them sits on an answer the user actually gave.** `scripts/test-branch.sh down` for this branch's environment may run at exactly two points, both of them a direct consequence of the user's own answer to an explicit question, and nowhere else. **The one-way door** is step 6, immediately after the user has explicitly answered "yes" to the literal question "Have you manually verified this in the browser?" — a one-way door because it leaves the branch with no environment. **The other** is step 1's rebuild branch, immediately after the user has answered "rebuild" to that step's own explicit reuse-or-rebuild question; there the `down` is followed at once by an `up`, so the gate still has an environment to verify in, and it is not a door at all. No other moment qualifies — not after your own exploratory use of the environment (implementation testing, debugging, a pre-check you ran to save the user time), not because you consider your own check equivalent to the user's, not as routine cleanup once you're "done" with it, not between two separate `/finish-cycle` invocations in the same conversation. If you used the environment yourself for any reason before reaching this gate, leave it running and let step 1 below discover it as already `up` — do not tear it down first "to keep things tidy" and re-spin it. Two real incidents in one session (2026-09-15, `worktree-costgrid-owner-reassign` and `worktree-planning-role-task-breakdown`) were both this exact mistake: the agent's own browser verification was mistaken for satisfying this gate, and the environment was torn down before the user had answered the question at all.

**Classification — is this a no-code cycle? (mechanical, before anything else below.)** Run `node scripts/classify-cycle.mjs`. Its first stdout line is the verdict, the rest are the paths it judged. **Only the literal `no-code` there makes this a no-code cycle** — anything else (`ordinary`, an error, a missing script, empty output, a non-zero exit) is an ordinary cycle, so a broken classifier cannot skip a verification. Record it as `<no-code-cycle>`; on an ordinary cycle do not raise the classification with the user. The rule lives in that script, pinned by `scripts/classify-cycle.test.js` — read the test, not a paraphrase. `PROCESS.md` §6.4c says why the branch exists.
- **The test is the path list, never a judgment about what the cycle is "about".** The name is deliberately "no-code cycle", not "process-only": `PRD.md` and `docs/prd/` are product documentation, which "process-only" would misclassify.
- **Named exceptions** — root `*.md` files the running app loads at runtime, which count as code — are the `RUNTIME_LOADED_ROOT_MD` constant in that script. The cycle that makes the app fetch one adds it there, with a test case. `TEST_CASES.md` is in it since 2026-10-09 (`test-cases.html` fetches and parses it at load), so a cycle touching only that file is `ordinary` — read the constant and `scripts/classify-cycle.test.js` for the current contents, never a count or a list from this prose.
- **On a no-code cycle:** step 0 below **still applies, subject to its own skip and scoping checks** — a prose-only diff is exactly where review earns its keep (one doc-split cycle produced 10 of its 16 findings on prose) — steps 1-5 are skipped, and step 6 takes its no-code branch. Two consequences, stated here rather than discovered: (a) no test environment is created, and **none is ever torn down on this path** — neither of the preamble's two licensed points is reachable here: the browser question is not asked, and step 1, which holds the other, is skipped. So a stack left running by an earlier attempt or session is *reported*, never removed (step 6's no-code branch says how); (b) because steps 2-5 are skipped, no Plan and no Spec is identified, so **Gate 4's out-of-scope check does not fire** — the 2026-10-13 extension of that check to the Spec does not reach this path, for the same reason — record that in the report instead of letting it vanish.

0. **Launch the code review now, in the background, so it runs during this gate — it becomes Gate 3's round 1.** `/code-review` is read-only: it cannot affect the branch, the stack, or the user's verification, so starting it here takes its wall-clock off the critical path instead of adding it after the "yes".
   - **`<reviewed-sha>` is defined here, once, and every path that uses it below — and in Gate 3 — means this.** It is the HEAD covered by a whole-branch `/code-review` of `main...HEAD` run in this session, whether that run is the one launched below or an earlier one. If more than one such review exists, `<reviewed-sha>` is the **earliest** of their HEADs: a scoped range must start at the oldest point not yet reviewed, so that nothing in between is skipped. A branch with no such review in this session has no `<reviewed-sha>` at all; every path that needs one states that precondition in its own words, and no such path may be taken without it.
   - **Skip this** if Gate 3's step 0 skip check applies **in full** — read it there rather than from a paraphrase: it also requires that every commit after the reviewed HEAD only applies fixes from that review and has itself been re-reviewed. If it does apply, that review stands and Gate 3 step 0 records the skip (PROCESS.md §6.4).
   - **If instead step 0b's precondition holds** — an earlier whole-branch review covers `main...HEAD` but HEAD has since moved by commits that are *not* its fixes — launch the review scoped to `<reviewed-sha>..HEAD` (as defined above), not the whole branch, for the reason 0b gives: re-reviewing the covered part is the double review §6.4 forbids.
   - Otherwise run `/code-review` at medium effort, scoped to the diff between the current branch and `main`, **as a background agent**, and continue immediately to step 1 — or, on a no-code cycle, straight to step 6. Note the HEAD this run covers — it is a `<reviewed-sha>` as defined above, which is what Gate 3 needs if HEAD moves during this gate, and the definition's "earliest of them" rule is what settles it against any earlier one.
     - If it genuinely cannot be backgrounded in the current harness, say so in one line and leave it to Gate 3, unchanged. Do **not** run it in the foreground here: that serialises it *ahead* of the human wait, saving nothing while making the gate look parallel.
   - **Do not show the findings, and do not apply a single fix, inside this gate.** A commit landing while the user is verifying would mean they verified a tree that no longer exists. They are shown and handled at Gate 3, and the question in step 6 is asked and answered exactly as before — a finished review is no input to it.

**Steps 1-5 apply only when `<no-code-cycle>` is false; on a no-code cycle go straight to step 6.**

1. Run `scripts/test-branch.sh status`.
   - If `down` (exit 1): ask explicitly "Spin up an isolated test environment for this branch now? [yes/no]"
     - If yes: run `scripts/test-branch.sh up`. Record `<branch-env-active>` = true.
     - If no: record `<branch-env-active>` = false, unless it was already true earlier in this same session (do not overwrite an existing true with false).
   - If `up` (exit 0): ask explicitly "An isolated test environment for this branch is already running (from an earlier `/finish-cycle` run on this branch) — reuse it, or rebuild it with fresh data from main? [reuse/rebuild]"
     - If reuse: do nothing further. Record `<branch-env-active>` = true.
     - If rebuild: run `scripts/test-branch.sh down`, then `scripts/test-branch.sh up`. Record `<branch-env-active>` = true.
2. Run `git log --diff-filter=A main..HEAD -- docs/superpowers/` to find spec/plan files added inside this branch.
3. Run `git log main..HEAD | grep -o 'docs/superpowers/[^ ]*\.md'` to find spec/plan files referenced in this branch's commit messages.
4. Run `git merge-base main HEAD` to get `<merge-base>` (this commit itself is included in the walk below, not just its ancestors), then `git log --oneline -8 <merge-base>` to list `<merge-base>` and the 7 commits before it — 8 chosen as enough to comfortably cover Brief+Spec and Plan as up to 2 separate doc-setup commits plus a safety margin, not a hard technical limit. Walk this list from `<merge-base>` backward and collect a *contiguous* prefix of commits whose messages match this project's own convention for spec/plan setup (`docs: brief + design spec for <topic>`, `docs: implementation plan for <topic>`) — stop at the first commit that doesn't match (do not skip over a non-matching commit to keep collecting further back). For each matching commit, run `git show --name-only <sha>` to get the `docs/superpowers/specs/*.md`/`docs/superpowers/plans/*.md` file(s) it added. This finds the common case in this project where Brief + Spec + Plan are committed to `main` *before* the feature branch is opened — steps 2-3 alone only see commits unique to the branch and miss this case entirely (a known, previously-reported blind spot). Bounding the walk to a contiguous matching prefix (rather than a flat commit-count lookback) avoids pulling in older, unrelated cycles' spec/plan commits once an ordinary merge or docs-sync commit is hit — though if a genuinely unrelated commit is ever wedged directly on `main` between a cycle's own Brief+Spec and Plan commits, this walk will under-collect (stop too early, missing the Brief+Spec found further back). This is a known residual gap, not silently unsafe: step 6 below still always asks for explicit manual-verification confirmation regardless of what this search finds, so the worst case is an incomplete candidate list shown to the user, never a skipped verification step.
5. Combine all three result sets (deduplicated):
   - Exactly one unique file → read it and check for mentions of browser verification or jsdom-untestable behavior. Show the file path and what was found (or state "no explicit mention of manual verification found in this file" if none).
   - More than one → state explicitly: "Found N candidates: [list] — no automatic selection."
   - Zero → state explicitly: "No spec/plan reference found in this branch's commits."
6. **If `<no-code-cycle>` is true, take the no-code branch in the first sub-bullet below and do not ask the browser question.** Otherwise — regardless of the outcome in step 5 — always ask explicitly: "Have you manually verified this in the browser? [yes/no]" — this question must reach the user and receive their actual answer; your own use of the environment earlier in this gate or anywhere else in the session is not a substitute answer, however thorough.
   - **No-code cycle branch (`<no-code-cycle>` true) — this is the whole of step 6 on that path; the two bullets below do not apply.** Do not ask the browser question: on this diff it has no honest answer — "yes" would be false and "no" stops the cycle — and a "yes" given as a formality erodes the very gate the two 2026-09-15 incidents created. Show `git diff --stat main...HEAD` **and** the full path list from the classification above (the `--stat` alone elides paths once there are many, and it is the classification being checked, not the content), then ask explicitly, without asserting the answer in the question: "Here is every path this diff touches — is this a no-code cycle? [yes/no]"
     - If the answer is "no", or anything other than a clear yes: the user is saying the **mechanical classification is wrong**, which is not the same as a failed verification — so do **not** stop. Set `<no-code-cycle>` to false and run the ordinary path instead: steps 1-5, then step 6's browser question, exactly as if the classification had never fired. Say in one line that you are doing so. (Stopping here would deadlock: a re-run reclassifies identically, and adding the file to the named exceptions needs a commit, which pre-flight check 2 refuses until the tree is clean.)
     - If "yes": run `scripts/test-branch.sh status` — read-only, not a teardown, so the preamble above does not bar it, and it is the only way to notice a stack this path would otherwise never discover (`<branch-env-active>` is never set here, since step 1 does not run). If it reports `up`, this branch has a test environment left running by an earlier attempt or session: **do not tear it down** — say so explicitly in chat and record it in the report, so it is left running knowingly rather than silently. Then proceed to Gate 3. The review launched at step 0 still has to be collected there and its findings handled — a no-code cycle does not skip Gate 3.
     - On a "yes", and only then, record in the Gate 5 report's **"Roadmap notes"** section that this gate took the no-code branch, that the browser question was not asked, and that Gate 4's out-of-scope check did not fire. That report is the only persistent trace of it. Put it in "Roadmap notes", not in the "Gate outcomes" section added 2026-10-12 — that section's one line per gate is for the outcome, this is the reason the gate took an unusual branch. Do not add a new field to the report template beyond what is already there, and do not write `0m (skipped)` for this gate — that is reserved for a gate that self-skips, and this one does ask a question.
   - If the answer is "no" or anything other than a clear yes: stop and wait. Do not proceed. Do not tear down the branch environment if `<branch-env-active>` is true — leave it running so the user can keep testing. If step 0 launched a background review, keep whatever it produced for the re-run: findings in hand, never a reason to skip a review of the commits that then fix the defect.
   - If "yes": if `<branch-env-active>` is true, run `scripts/test-branch.sh down` to tear down the test stack — this is the one-way door the preamble above names, and the no-code branch reaches neither of its two licensed points. Then proceed to Gate 3.

## Gate 3 — CODE REVIEW (conditional human gate, max 3 rounds by default)

**First, collect the background review.** If Gate 2 step 0 launched one, wait for it and treat its findings as this gate's round 1: start `code_review_followups` as an empty list (step 1 declares it, and that step is skipped on this path), and then — **before step 2** — close the one gap this path can leave: if HEAD has moved past `<reviewed-sha>` (defined at Gate 2 step 0), because a commit landed during Gate 2 (typically a visual correction), run step 0b's scoped review of `<reviewed-sha>..HEAD` as well and add its findings to the round. Without that, those commits reach Gate 4 with no review at all. Then go to step 2 with the combined findings; steps 0 and 0b are not otherwise re-entered on this path. If it produced nothing usable — the agent died, timed out, or returned no readable findings — say so in one line and treat the diff as **not reviewed**, running step 1 normally. A run that cannot be read is never a clean review, and nothing below may conclude otherwise.

**Recording for the report, on every path.** However round 1 is obtained — backgrounded from Gate 2, run at step 1, or not run at all — record its **total finding count** and **how many of those findings fall in Gate 1 step 0's four mechanical classes** (a false predicate, a stale number, a wrong SHA or adjacency, an incomplete enumeration), plus **the minutes the re-checks below cost**. All of it goes in the report's claims pre-check line, in prose: say what did not happen rather than inventing a zero. If round 1 came from step 0b's scoped path, say so — it counts over a subset of the diff the Gate 1 pre-check read. Classifying a finding is a judgement: when it is genuinely unclear, leave it out of the mechanical count rather than inflating it.

0. **Skip check (no double review of the same diff, PROCESS.md §6.4).** Note since 2026-10-13: on any branch where Gate 1 step 0 found something, its `docs:` commit is not a fix from any review, so this full skip cannot fire. What replaces it is **not automatically** step 0b: 0b still needs an earlier whole-branch review of `main...HEAD` in this session, and a branch may simply not have one — native execution has no per-task review, and whether its final whole-branch review was run in this session is a fact to check, not to assume (§6.4). With one, 0b's scoped path applies; without one, step 1 runs a normal full review. Do not claim the scoped path on a branch that never had that review — it would leave everything but the pre-check commit unreviewed. If, earlier in this same session, a whole-branch review covered `main...HEAD` (e.g. the final review of `superpowers:subagent-driven-development`), and every commit after the reviewed HEAD only applies fixes from that review and has itself been re-reviewed, do not run `/code-review`. State explicitly: "Code review: skipped — the final whole-branch review at `<sha>` already covers this diff (fixes `<sha..sha>` re-reviewed)." Carry that review's accepted follow-ups into `code_review_followups`, note the skip in the report's Roadmap notes, and proceed to Gate 4. If any condition is not met, or the review happened in another session, run step 1 normally.
0b. **Scoped-review path (partial skip).** If a whole-branch review covered `main...HEAD` earlier in this session but HEAD has since moved by commits that are *not* fixes of that review (typically Gate 2 visual corrections), do not re-review the whole branch: run `/code-review` scoped to **only those commits** (`<reviewed-sha>..HEAD`, defined at Gate 2 step 0). State explicitly: "Code review: scoped to `<sha>..HEAD` — the whole-branch review at `<sha>` already covers the rest." Since the review now starts at Gate 2, a fix born at that gate is by construction newer than the reviewed HEAD, so for those fixes this scoped path is the **norm, not a case to argue each time**. Rationale (PROCESS.md §6, "esecuzione proporzionata"): in the Cost Grid A cycle the full `medium main...HEAD` sweep ran after the Opus whole-branch review for two small CSS/markup commits (+119/−48), took 18 minutes across 10 agents, and produced **zero** code changes — 3 of its 8 findings were already parked by the earlier review, one restated another, and one was outside the spec's scope.
1. Unless round 1 was already collected from Gate 2 (see the paragraph above), run `/code-review` at medium effort, scoped to the diff between the current branch and `main`. This is round 1. Maintain a running list, `code_review_followups`, starting empty.
2. If the review reports zero findings: state this explicitly ("Code review: no findings.") and proceed automatically to Gate 4 — no confirmation needed.
3. If the review reports one or more findings:
   - Show all findings.
   - **Round 1 asks; later rounds may not need to.** Ask explicitly: "Fix now, accept as follow-up, or a mix (specify which)?" From round 2 on, if the round-1 answer stated a **rule** rather than a list ("all follow-up except correctness"), apply it instead of re-asking, report the application ("round 2: 3 findings, 1 fixed under your rule, 2 to follow-up"), and stop only on a finding the rule does not cover. **If round 1 was decided finding by finding, no rule is inferred from it** — same "never inferred" principle as PROCESS.md §6.4c and `feature-brief`'s scenario question. PROCESS.md §6b calls this a class-D gate: the decisions are real, the repeated question is not.
   - For every finding the user accepts as follow-up, append it to `code_review_followups`, tagged with the current round number.
   - For every finding the user chooses to fix now, apply the fix.
   - **Before re-running the review, re-run Gate 1 step 0's four checks over the fixes you just made** (`git diff HEAD` if they are still in the working tree, the round's fix commits if you already committed them; `*.md` only, same four checks, same "fix the predicate, not the line"). This is the step's main point of leverage, not a flourish: M7's measured mechanism is that most of each round's findings were created by the *previous* round's own fixes, so a pre-check that only ever ran at Gate 1 would have prevented its round 1 and nothing after it. Count the defects found here **separately** from step 0's: they are evidence about this re-run, not about the Gate 1 pass, and merging them would let one mechanism's catch vouch for the other's. Then run the tests that cover what this round actually changed. For `*.md` fixes that is `npx vitest run scripts/ js/lib/test-cases-parse.test.js` — `scripts/` alone is not enough, because the pre-check reads every `*.md` the branch touched and `TEST_CASES.md`'s counts are pinned outside it. **For a round that fixed code, it is the test files covering that code** (`npx vitest run <file>`, or `docker exec pdash-api node --test src/<file>` for backend): the two markdown targets exercise none of it. The whole suite is deliberately not prescribed here — PROCESS.md §6.2's discipline is targeted runs during work — but **this gate is never left red**, whichever path exits it, including the one that accepts everything as follow-up. These edits land after Gate 1's suite, so a guard they trip would otherwise surface at Gate 5 step 3, post-merge on `main`.
   - If any fix was applied and the round just completed was round 1 or round 2: run `/code-review` again on the same scope (this becomes the next round) and repeat step 2/3 for it.
   - If any fix was applied and the round just completed was round 3 (i.e. a 4th run would be required by the normal flow): do not silently re-run. Instead:
     - State explicitly: "3 rounds of code review in a row have produced findings — this suggests a more structural issue than an isolated fix, not just noise."
     - Show the full sequence of findings across all three rounds, not just round 3's.
     - Ask explicitly among exactly three options: "(a) continue past the limit with another review round, (b) accept everything remaining as follow-up, or (c) stop the cycle to reconsider the approach."
     - On (a): run another round and treat it like any other round — the user has explicitly opted past the default cap, so no further hardcoded limit applies.
     - On (b): append all remaining findings to `code_review_followups` and proceed to Gate 4.
     - On (c): stop `/finish-cycle` entirely.
4. Once the gate is passed (zero findings, or all remaining findings accepted as follow-up), proceed to Gate 4, carrying `code_review_followups` forward for use in Gate 5.

## Gate 4 — MERGE (step 2's confirmation is the only human gate here; every other step, the merge at step 5 included, runs automatically once it is given)

1. Build the pre-merge summary:
   - Commit count: `git log main..HEAD --oneline | wc -l`
   - Files touched by category: run `git diff --stat main...HEAD`, then group the listed files by top-level path prefix (`js/`, `api/`, `css/`, `docs/`, or "root-level" for any file with no `/` in its path).
   - Out-of-scope check: from the candidates Gate 2's step 5 collected, take the **Plan** if there is exactly one; if this branch has no Plan, take the **Spec** if there is exactly one. Read the chosen file's "File Structure" section (a markdown table or list of file paths near the top) and compare it against the files touched in this diff. List, non-blocking, any touched file not mentioned there as "outside the declared File Structure." The Spec is a fallback, not an equal: it may declare its file structure more loosely than a Plan does, or not at all — if the section is absent, say so in one line and skip the comparison, rather than reporting every touched file as out of scope.
   - **This check does not fire when Gate 2 identified no artefact at all, and the extension above does not change that.** That covers every no-code cycle — steps 2-5 do not run there, so there are no candidates, Plan or Spec (measured on the `claims-precheck-gate1` cycle, 2026-10-13, where exactly this happened) — and equally an ordinary cycle whose step-5 search came back empty or with more than one candidate of the kind being used. Gate 2's no-code branch records the non-firing in the report; nothing here claims to cover that case.

## Gate 6 — FINAL REPORT (in chat)

**The report file written at Gate 5 is the register — this gate does not restate it.** It is the only persistent artefact, and for the project memory it is the only trace that exists at all. Until 2026-10-12 this gate printed the memory line, which was already in the file, and a per-gate outcome line that was **not** anywhere in it — so removing the duplication required adding the report's own "Gate outcomes" section (step 2 above) rather than simply dropping the lines. PROCESS.md §6b is the rule. Print in chat only:

- The path to the just-committed report file.
- **One** outcome line for the whole cycle, naming only what was not routine (e.g. "Merged and pushed; 1 review finding fixed, 2 deferred" or "Merged and pushed; clean"). Not one line per gate.
- The items that need a **human action after this cycle** — accepted code-review follow-ups and anything in Roadmap notes that is a task rather than an observation — or "nothing open" when there are none, followed by: "See the Gate outcomes and Roadmap notes sections of `<report path>` for the per-gate detail and the full list."
- **REQUIRED, as the literal last line, with nothing after it:** `Cycle closed and pushed. If this was the last of a series of related cycles (e.g. a multi-cycle audit), consider a cold review before moving on to the next work.` This is a fixed, unconditional closing line, not optional trailing commentary — it is a text suggestion for the user to weigh, not a decision this command makes: never try to determine from repo state, commit history, or anything else whether this cycle actually was the last of a series — always print the same line, and never act on it (no starting a review, no reading other reports) beyond printing it.
