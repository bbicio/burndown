# operational-manual (standalone)

Turns whatever planning/reference material a project has — or what the user says directly — into a manual for the people who will actually use the finished application. A translation into operational register, not a new source of truth, and not tied to any particular development process or file-naming convention.

## Produces

A single, self-contained HTML file (`docs/OPERATIONAL_MANUAL.html`, or wherever the project's docs live — confirm the path if unclear). Every point has a concise, always-visible description; where real extra depth exists in the source material, that point also gets a `<details><summary>▸ Details</summary>...</details>` block — collapsed by default, independent of every other point (opening one never affects any other, and never moves scroll position). A `<details>` body may include a small **controls/button reference table** (Control · What it does · Who sees it) where the source material names several distinct controls for that flow, and/or one embedded screenshot with a caption when the generation run included a screenshot pass.

**Chapter and section numbers are always sequential, starting at 1 — never mirrored from the source's own numbering.** A source document's own section numbers (e.g. `PRD.md`'s) can have gaps or start above 1 from historical reorganization — meaningless, and confusing, to a reader of the manual who has never seen that source. Number the manual's own chapters 1, 2, 3, … with no gaps, regardless of what the source calls them, and number sub-sections `N.1`, `N.2`, … within their own chapter the same way. Every in-text "§N" cross-reference in the body must use the **manual's own** numbers, not the source's — when mapping source sections onto manual chapters (Step 2), keep a mapping table for the duration of the writing pass so every cross-reference gets translated consistently.

**Every heading is a real anchor, and every cross-reference is a real link.** Every numbered heading — chapter (`<h2>`) and sub-section (`<h4 class="sub">` or equivalent) alike — carries a stable `id` attribute derived from its own number (e.g. a sub-section numbered 7.2 gets an `id` such as `s7-2` or `clients` — pick one convention and apply it uniformly across the whole document). Any in-text reference to another part of the document (a parenthetical like "(§7.2)", "see §4", "covered under Sharing") must render as `<a href="#that-id">§7.2</a>`, never as plain unlinked text — a reader following the logic of a cross-referenced explanation (e.g. a rate fallback chain spanning §4/§7.2/§7.6/§7.7) must be able to click straight to each link in the chain. When adding or renumbering a section, update every existing in-text reference that pointed at its old anchor.

The page also carries:
- A **provenance stamp** near the top: generation date and version number only — no source-material or scope notes (these add no value to the end reader the manual is written for; keep that context in the skill's own commit history / Changelog table instead).
- A persistent, **append-only Changelog table** (columns: Version · Date · Title · Description) — one row per numbered release, never regenerated from scratch: always read the existing file's Changelog table first (if the file already exists) and preserve every prior row verbatim, prepending only the new one. Version numbering starts at **v1.0** for the first generation produced under this table-based scheme; any earlier, unversioned generation of the manual does not get a row here (its own history lives in git, not in this table). See the "Versioning" step below for how a version number is chosen at each run.

English by default, unless the user asks for another language.

## Steps

1. **Locate source material — don't assume a fixed structure.** Look for existing docs that describe roles, permissions, and feature behaviour (common names: `PRD.md`, `ARCHITECTURE.md`, `README.md`, a wiki, existing user docs). If found, read them. If nothing suitable exists, or what exists is ambiguous, **ask the user** what to read from, or ask them to describe roles and flows directly — never infer silently from a guess at file names.
2. **Establish the organizing structure.** From the confirmed source, decide whether the manual reads best organized by role (e.g. admin/member/guest) or by flow/page — this is a real per-project decision, not a default; see the project-specific defaults below for how it was resolved here.
3. **Confirm what's actually live.** Before describing any feature, confirm with the user (or check against a real, current signal) that it's genuinely in production, not just planned or in progress. **Never document a capability that isn't live** — a manual promising something unbuilt is worse than no manual. If a source enumerates features already, extract that list and confirm it **once, cumulatively**, rather than one question per feature.
4. **Write the concise pass first, for every point, before touching any `<details>` expansion.** Plain operational language — no implementation detail (no component names, no architecture, no internal IDs), no jargon the audience wouldn't use. A user thinks "how do I add a new record," not by the internal name of the code that does it.
5. **Decide what gets a `<details>` expansion — by re-reading the source against the concise pass just written, not from a fixed checklist.** A point earns an expansion when the source material genuinely contains more than the concise sentence kept — a fuller formula, a concrete example, an edge case, a safety mechanism, a constraint a reader would want to know before acting. Where a flow is genuinely hard to trust from a formula restatement alone (a calculation chain, a multi-step mechanism with a counter-intuitive rule buried in it), write the expansion as a real walkthrough — structure, then the mechanism step by step, with the one or two genuinely counter-intuitive rules called out explicitly — not a denser repetition of the concise sentence. Where several distinct named controls exist for one flow, add the controls-table pattern from "Produces" above instead of, or alongside, prose.
6. **Screenshot pass (only when the generation run is scoped to include it — confirm with the user first if unclear).** For each major flow worth illustrating (roughly one per significant page/view — a starting checklist, not a fixed contract; drop a flow that can't be captured rather than blocking the whole run):
   - Bring up an **isolated environment with synthetic-only data** — never the project's real/production data. If the project's own tooling clones real data by default when spinning up an isolated environment, explicitly avoid or bypass that path (start from an empty/freshly-migrated database instead) and seed a small, obviously-fictional data set sufficient to populate the flows being captured.
   - Capture one screenshot per flow, embedding each as a `data:image/...;base64,...` image directly in the HTML — never as a separate linked file — so the page stays one portable document. Give each a one-line caption.
   - If a specific capture can't be completed after one reasonable retry, ship that point without an image (optionally an HTML comment noting the gap) rather than blocking the rest of the generation.
   - Tear the isolated environment down when done, per the project's own infrastructure-safety conventions.
7. **Assign every heading a stable anchor `id`, and turn every in-text cross-reference into a real link to it** — see "Produces" above for the convention and the rule this enforces. Do this pass after content is finalized (step 4/5), so anchors aren't assigned to sections that later get cut or merged.
8. **Decide the version number with the user before finalizing — never silently.** If this is the first generation produced under the table-based Changelog scheme, it is **v1.0**, no confirmation needed beyond stating it. For every later run, ask the user what this generation's version bump should be (e.g. "this adds the timesheet validation section — patch, minor, or major bump from v1.0?") — this is a judgment call about how significant the changes are, not something to infer silently from the diff size.
9. **Update the Changelog table.** If regenerating an existing file, read its Changelog table first and carry every row forward unchanged; prepend one new row — Version (from step 8) · Date · a short Title · a one-sentence Description written from actual knowledge of what changed since the last entry (the same judgment as a commit message, not a mechanical diff of the regenerated HTML, which would be noisy since the whole file is rebuilt fresh each run). The v1.0 row's Description is purely declarative ("First versioned release.") — it has no prior version to diff against.
10. **Stamp the generation date and version number** in the provenance block at the top (see "Produces" above for what belongs there and what doesn't) — so a future reader can judge how current the page is at a glance.

## PDash-specific defaults

These answer, for this repo specifically, the questions the generic steps above would otherwise ask each time:

- **Source of truth: `PRD.md` only.** It is already organized by feature/page in user-facing language and is kept in sync with what's actually merged to `main` (updated at every `/finish-cycle` Gate 5, only for shipped behavior — never for roadmap or in-progress work; and periodically reconciled by a `domain-audit` pass against the live codebase, most recently `docs/superpowers/audits/2026-09-16-prd-vs-app-behavior-audit.md`). Do not read `ARCHITECTURE.md` or `CLAUDE.md` as source material — both are implementation-detail documents (file paths, Vue internals, SQL) and pulling from them risks violating the "no implementation detail" guard below.
- **"Confirm what's live" (step 3) is a light pass here, not a full audit.** Since `PRD.md` is already scoped to merged behavior by construction, treat it as live by default; still ask one cumulative confirmation question before finalizing, as a safety net.
- **Structure: by flow/page, not by role.** PDash's permission model is two independent axes — a global role (`user`/`admin`/`sysadmin`) and a per-resource permission (`owner`/`editor`/`viewer`, which can differ project-by-project for the same user). A strict one-section-per-role structure would duplicate every flow 3-4 times. Mirror `PRD.md`'s own organization (by page/feature) and note permission differences inline within each flow (e.g. "viewers cannot see this button").
- **Language: English**, matching CLAUDE.md's project-wide constraint that all user-facing text must be in English — the manual describes an English-UI product, regardless of what language the request to generate it arrives in.
- **Output path:** `docs/OPERATIONAL_MANUAL.html`. (A prior plain-Markdown generation at `docs/OPERATIONAL_MANUAL.md` was superseded and removed 2026-09 — this skill produces only the HTML file now.)
- **Visual template: frozen as of the 2026-09-17 first generation, user-approved — amended 2026-09-17 for the versioning/anchor changes below, then frozen again at the new shape.** Every future regeneration MUST reuse the existing file's `<head>` (`<style>` block, fonts, color tokens, dark-mode media query) and overall `<body>` structure (masthead, provenance bar, sticky TOC, `.chapter`/`.item`/`details.expand`/`table.controls`/`table.fields` markup and classes) **byte-for-byte** — read the current file first and copy its CSS/shell verbatim, editing only: (a) section content, (b) the provenance stamp (now just date + version — no Source/Scope lines, see "Produces" above), (c) prepending one new row to the Changelog **table** (Version · Date · Title · Description — no longer free-text `.cl-entry` blocks), (d) the `id` anchors and in-text cross-reference links required by the "Every heading is a real anchor" rule above. Do not redesign, re-theme, re-palette, or restructure the page beyond exactly these amendments on this run, and do not restructure it further on any *future* run, even if a later `artifact-design`-style pass would produce something "nicer" — the point of freezing it is that regenerations must never visibly reflow or re-skin the document a reader already knows. If the content genuinely needs a new UI pattern this template doesn't have (e.g. a new kind of table), add it as a minimal, consistent extension of the existing CSS system (reuse the existing token variables and class-naming convention) rather than introducing a new one — and note the addition in that run's Changelog row.
- **Screenshot environment:** `scripts/test-branch.sh`, started with a fresh/empty database (bypass its default clone-from-main behavior) and seeded with obviously-fictional demo entities (a demo client, offer, project with tasks/roles/actuals, a program, a POT) — never the main stack, never real client/project data. Tear down with `scripts/test-branch.sh down` when the screenshot pass is complete, per this project's own Docker-safety convention (see `CLAUDE.md`'s "Infrastructure safety" section).
- **Detail-content candidates:** see the dedicated "PDash detail-content reference" section below — kept inline in this skill file (not just referenced from the design spec) specifically so it survives future runs even if the spec document is ever moved, archived, or forgotten.
- **Screenshot checklist (starting point, ~10-14 captures):** Pipeline board, offer detail panel, cost grid/offer editor (a role column with a custom-rate badge visible, compact mode off so the move/change/dup/remove controls show), the selection-mode toolbar with the Create Program modal open, the proposal's inline "Shared with" list, Resource Planning (By Role expanded, and optionally a second capture of By Owner — this table's structure genuinely differs enough between views to warrant more than one), Project Reporting's project list (a program group with children visible, filters in use), a single-project detail page (burndown chart populated with both reference lines), the project configuration form (a multi-month task with its % distribution grid and validation badge, plus the PTC section), timesheet upload/actuals, the Currencies admin tab, and the Pipelines & POTs "View Details" modal. Trim or extend this list at generation time based on what's actually feasible to capture in the isolated environment.

## PDash detail-content reference (as of 2026-09-16)

This is the living answer to Step 5 for this project — not a fixed checklist, a **starting point** kept inline so it survives independently of any spec document. Built by re-reading the entirety of `PRD.md` section-by-section against a first concise draft, then again after a full `domain-audit` pass (`docs/superpowers/audits/2026-09-16-prd-vs-app-behavior-audit.md`) closed 14 further gaps in `PRD.md` itself. **Maintain this section at every future run**: re-derive it the same way (a full side-by-side re-read of the current `PRD.md` against the current concise draft), add anything new found, and correct or remove anything here that `PRD.md` no longer supports — never treat this list as a ceiling, and never let it silently go stale the way `PRD.md` itself did before the 2026-09-16 audit.

**§2 Getting started**
- **Login and password recovery — anti-enumeration behavior.** Both login failures and password-reset requests respond identically whether or not the email matches a real account, specifically so no one can use either form to discover which emails are registered. Worth a short `<details>` even with little extra prose to add, since it's a real applicative flow worth keeping in scope.

**§4 Pipeline**
- **Offer cards** — the exact visibility rule for the Delete button (Draft-stage cards only, and only with edit permission), not just "editing/deleting needs edit access."
- **Mixed-currency column totals** — a column holding offers in more than one currency shows one subtotal per currency (in that currency's own figures) plus a combined EUR-equivalent total, rather than one blended number; a single-currency column just shows a plain total.
- **Version-level actions** — beyond the locking conditions covered under "Offer editor," a version itself carries Duplicate, Delete, and JSON export/import actions, and multiple versions of the same offer are switched between via tabs above the detail panel/editor.
- **Saving in the offer editor** — every field edit (phase/task names, descriptions, PTC, header fields, role rates) autosaves in the background with a brief confirmation toast, with no explicit save required; a `💾 Save` button is also available for an immediate save, separate from the autosave.
- **Filtering** — the Value filter's bucket ranges spelled out (€0–20K / €20K–50K / €50K–100K / €100K–200K / €200K+) and what "Include PTC" changes; the explicit OR-within-one-filter / AND-across-filters rule; that filters reset on every page reload; that the Draft column is exempt from all filtering.
- **Detail panel** — the full header action list and that deleting a proposal's only remaining version deletes the whole proposal, not just that version; every left-column field (rate card name if set, JSON export button); that a linked project's "Project Dashboard" button only appears once timesheet data exists for it; the full right-column phase/task/role/grand-total breakdown structure.
- **Board toolbar** — that switching pipeline year changes the URL (`?year=YYYY`) and that "+ New Proposal" is hidden for non-admins on inactive years.
- **Offer editor** — the full field split between grid-level and version-level settings; the role rate fallback chain (client rate card override → role's per-currency agency default → EUR rate × currency exchange factor); the two distinct locking conditions (Committed + fully migrated, OR a sibling version already has a linked project). **The Currency field (2026-09)**, whenever a non-EUR currency is selected, shows the offer's own "1 EUR = X" rate underneath it — this is the rate the offer was created or last saved with, frozen, not a live lookup against the Currencies admin tab; reinforce this with the same non-retroactivity point covered under §13/§16's Currencies bullet.
- **Task-level cost — walked through the same way as Resource Planning below, since Resource Planning's own "Sold" figure ultimately comes from here:**
  1. **The unit is hours, not days.** Each task-role cell in the offer editor is an hours figure, entered directly — not a day count converted into hours.
  2. **Task cost** = Σ(hours × that role's effective rate) across every role on the task, plus that task's own pass-through costs.
  3. **Phase cost** = the sum of its tasks' costs; **offer total** = the sum of its phases' costs. Pure sums at both rollup levels, nothing re-derived or re-rated.
  4. **The bridge to a project.** When a task is migrated into a project, each role's hours figure carries over unchanged into that role's `soldHours` on the new project task — a direct copy, no recalculation or conversion.
  5. **The bridge to Resource Planning.** Resource Planning's "Sold" column is exactly this same `soldHours` figure, summed however the active grouping view calls for — a number seen there traces back, unchanged, to what was typed into the offer editor's hours cell.
- **Role column controls** — each role column has four per-column actions: move it left/right, replace ("change") the role while keeping its position and hours, duplicate the column under a different role, or remove it outright; the editor's compact-header toggle hides all four to save space and can be switched back off to restore them.
- **Editor toolbar: Publish to SIP, Share, Clone, Export XLS.** **Publish to SIP** is a one-way transition (a published version can never go back to Draft) that also permanently deletes any *other* Draft versions of the same proposal, named explicitly in the confirmation dialog before it happens. **Share** in the editor is the same mechanism covered under Sharing and Permissions (§18 below) — cross-reference rather than re-explain, but note the inline "Shared with" list (with per-share removal) lives inside this same editor form, not only on the pipeline board's detail panel. **Clone** creates an entirely new, separate proposal (not a new version of the current one) by copying the full phase/task/role structure, always starting at version label "v1" regardless of the source version's own label. **Export XLS** downloads a styled Excel workbook of the current version's full structure.
- **Linked projects in the editor form** — same presentation as the pipeline board's detail panel (status + Project Dashboard link once timesheet data exists), not two different implementations to describe separately.
- **Generating a project from an offer (task migration + Program auto-link)** — covering all three real scenarios:
  1. **Selecting every remaining task at once** — a single project is created immediately, no program step, no prompts.
  2. **Selecting only some of the tasks (partial)** — if the offer has no program yet, a "Create program" step appears (create new, or link to an already-existing one); canceling aborts the whole generation with nothing created; once a program is established this way, every later generation from the same offer — partial or the remaining full set — auto-links to it with no further prompt. Any editor of the offer can do this, not just admins. If the underlying save fails to reach the server, the app shows an explicit sync-failure warning rather than a false success message.
  3. **Assigning selected tasks to an already-existing linked project instead of generating a new one** — the same selection toolbar offers a dropdown of the offer's existing linked project(s) plus a "＋ Add to project" button once at least one exists; a confirmation step lists exactly which tasks will be added; the dropdown always resets after use.

**§5 Resource Planning**

Write this section as a genuine walkthrough, not a compressed formula restatement — without a clear explanation of what populates the table, the numbers are hard to trust. Structure it in this order:

1. **What a row means, per view.** **By Role** — one row per role, expandable (collapsed by default) into one child row per (project, task) combination that role covers. **By Project** — Project → Task → Role → Owner, the most granular view. **By Owner** — Owner → Project → Task, a *coarser* view by design: hours from every role a person logged time under on a given task are combined into that one task row, because the view's purpose is "what is this person actually working on," not their role — role-level detail is what By Project is for.
2. **What the columns mean.** Time-period columns (months or weeks) across the selected date range, plus three summary columns regardless of grouping: **Sold**, **From actuals**, **To be planned**.
3. **Sold** — estimated hours from the offer/project's own task-role data, summed to match the row, filtered by the active Team filter if set.
4. **From actuals** — for past periods only, matching timesheet hours actually logged, matched to the row's task/role by name (case-insensitive, tolerant of a missing task name).
5. **Residual, and the one genuinely counter-intuitive rule.** Residual = `max(0, Sold − From actuals)`, computed **per individual task/role, never at the row's aggregate level**, then floored at zero. This is *why* "To be planned" can sometimes be bigger than "Sold minus From actuals" suggests: if one task among several is already over-consumed, its own shortfall floors to zero and stops contributing — it does **not** pull down other, still-healthy tasks' remaining residual. The app itself flags this with a tooltip; state it the same way: **intentional, documented behavior, not a bug.**
6. **To be planned — how the residual spreads across future weeks.** If the task's own month-by-month `%` distribution sums to ~100%, the residual follows that distribution, re-proportioned across whichever future months it covers. Otherwise, split evenly across the task's own remaining weeks — counted from the *task's own date range*, not the visible date window, so hours-per-week doesn't change as the user pages through the calendar.
7. **Monthly pulse.** Only in the even-split path, only when it would put less than 1 hour/week on a task — the whole month's share shows once, on that month's first week, proportional to how many calendar weeks fall in that month. Also computed from the task's own canonical week count, so it doesn't reshuffle on paging either.
8. **Rounded toggle.** Purely cosmetic — whole numbers vs. two decimals. Never changes any total or export.
9. **The Gantt view uses different, simpler math — by design.** Task-level, not phase-level. Bars show `min(100, consumed/sold × 100)` as a completion indicator — raw sold hours split evenly (or by the `%` distribution), with consumption overlaid separately, never subtracted the way the table's residual math does. The two views answering different questions is expected, not an inconsistency.
10. **Overallocation color coding.** A static, non-AI legend: a row's load shows red once it exceeds 30 hours/week. State plainly that this is a fixed display rule, not an analysis — see §11's note on a feature this PRD once incorrectly described as an AI-driven version of this same idea.
11. **📂 Load XLS.** Resource Planning has its own upload button for the same actuals-import mechanism covered in §8 — mention it here as a cross-reference (third entry point) rather than re-explaining the upload flow.

**§6 Project Reporting**
- **The two KPI tables are not interchangeable** — the portfolio summary's "Budget Estimated" reads the manually-maintained `phasing` grid, while the drill-down's "Total Budget" is computed live from task sold-hours × rate; the two can disagree if `phasing` hasn't been kept in sync (e.g. after editing sold hours without re-running Derive/Reforecast).
- The full Portfolio KPI formula table (Estimated/Spent/Variance) and the full per-project drill-down KPI formula table (6 rows: Total Sold Hours, Total Budget, Hours/Budget Consumed, Hours/Budget Left).
- **Monthly Summary Table** — the exact Hours/Budget formulas per column, and that variance highlighting is one-sided (negative shown in bold red; no corresponding green for positive variance).
- **Burndown chart** — the one chart on the single-project dashboard: a filterable (single task or whole project; monthly or weekly) line chart whose solid line is actual consumption ("Remaining Hours" if the project has a budget, "Cumulative Hours" if not), against up to two dashed reference lines — phasing-derived estimated budget and/or planning-derived estimated hours — so a reader sees at a glance whether consumption is running ahead of or behind plan. Together with the KPI cards, Monthly Summary Table, and the Summary-by breakdowns, this is the complete "information and reports" surface of the single-project dashboard.
- **Summary by role** — the concrete example (a role billed at two different hourly rates on two different tasks, e.g. "Account Director" at 168/h on one task and 130/h on another).
- **Summary by functional area** — the `{role, task}` membership model (a role can be claimed on one specific task while excluded on another, vs. the legacy "any task" wildcard).

**§7 Project Configuration**
- The full Project fields table and Task fields table (exact field list, types, matching rules against the timesheet columns).
- **Derive vs. Reforecast** — the specific rounding/drift-carry behavior, the blocking-error case's exact message shape, and — importantly — **that there is no snapshot/rollback and no unsaved-changes warning**: a successful run only updates on-screen values until Save is clicked, and navigating away first loses it silently with no `beforeunload` prompt.
- **Actuals section** — the exact filename pattern for downloaded actuals, and that the "View" popup's Fee/Spent columns come from the rate snapshotted at import time, not a live lookup.
- **Monthly % distribution per task** — only appears for a task spanning more than one month; one editable percentage cell per covered month, with a live badge showing whether the row currently sums to 100%; cells lock once the task is marked Completed, for a single-month task, or for a viewer. This is the direct input Derive/Reforecast read — explain it before the comparison table.
- **Monthly Budget Phasing / Monthly Hours Planning grids** — plain, freely-editable input grids by default; Derive/Reforecast are bulk-fill shortcuts *on top of* these same grids, not a separate mechanism.
- **Pass Through Costs (PTC)** — a project-level section (distinct from the cost-grid task-level PTC): individual external-cost line items (title, optional note, amount, a month chosen from the project's own configured months), a running total, per-item removal.
- **Functional Groups** — the `{role, task}` membership model, the "— any task —" wildcard; cross-reference the dual-rate example already used under Summary by role rather than re-explaining it.
- **A Program's ID is permanently fixed after creation** — no way to correct a typo later; the only workaround is creating a new program and migrating its projects.
- **Deleting a Program is blocked outright while any project is still linked to it** — state the real (blocking) behavior; the app's own confirm-dialog text is misleading here (implies projects get silently unlinked) but that's a separate, tracked product bug, not something the manual should describe as real behavior.
- **Programs no longer has its own tab in Configuration's navigation (2026-09).** Program creation happens elsewhere (the project configuration form's "+ New program", or the auto-link step when generating a project from an offer, §4.9) — a reader looking for a dedicated Programs screen in Configuration won't find one. Renaming or deleting an existing program currently has **no UI entry point at all** — state this plainly as a known, accepted gap, not something to gloss over or imply a workaround for.
- **Configuration's tab order (2026-09)**: Currencies, Roles, Clients, Client Groups, Pipelines & POTs — worth naming explicitly if the manual walks through this page tab-by-tab, since it no longer matches an older left-to-right assumption.
- **Deleting a Client Group only ungroups its member clients** — doesn't delete them. A client belongs to at most one group at a time.

**§8 Timesheet Upload**

Write this with the same walkthrough treatment as Resource Planning above:

1. **Where you upload from.** Three entry points that are the *same* underlying action, each with its own "📂 Load Actuals" (or, on Resource Planning, "📂 Load XLS") button: the project's own configuration form, the Project Reporting single-project detail page, and Resource Planning.
2. **What the file needs to contain.** The exact expected-columns table (Date, Job Role: Name, Owner: Name, Hours, Task/Issue, D365 Project ID, WF Project Name, Notes) with each column's format and matching rule.
3. **What happens to each row on upload.** A row with a missing/blank D365 Project ID is skipped entirely; a row with a project ID but incomplete data otherwise (blank date or hours) is still stored as-is. Rows are grouped by project code.
4. **Role/task validation — checked before anything else, and it can block the whole upload.** Every row's task and role are checked against that project's own configured tasks/resources; if even one row references a task that doesn't exist on the project, or a role (blank included) that isn't among that task's configured resources, the **entire file is rejected — nothing is imported, for any project code in the file** — and a dialog lists every distinct project/task/role combination found to be inconsistent, so the file or the project's configuration can be corrected before re-uploading. This check runs first, ahead of the replace-not-append and rate-snapshot behavior below.
5. **Replace, not append — the single most important behavior to get right, once the file passes validation.** Uploading a new file for a project code **replaces every previously-imported row for that code**, it does not add to them.
6. **The rate snapshot.** Each row's hourly rate (Fee) is resolved and locked in once, at import time. A later rate change doesn't retroactively affect already-imported rows — re-uploading is the only way to pick up a rate change.
7. **Date parsing.** Unambiguous whenever one date number is >12; falls back to MM/DD only when genuinely ambiguous; a date that isn't a real calendar date rejects the **entire upload**, naming the offending row.
8. **Reviewing/managing what was uploaded, afterward.** The admin-only Timesheet Management page's columns (Client/Project/Project code, Uploads, Rows, Last uploaded) are independently sortable (ascending → descending → unsorted); its pipeline-year selector defaults to the current calendar year if active, otherwise the most recently active year, with an explicit "All years" option. Downloaded exports use the filename pattern `<Client>_<Project>_<ProjectCode>_<YYYYMMDD>.xlsx`.

**§13/§16 Administration**
- **Roles registry — the missing middle link of the rate fallback chain.** Beyond label/code/team/default EUR rate, the Add/Edit Role form has one extra field per active non-EUR currency — "Default rate (X/h)." Blank means "convert the EUR rate at the current exchange rate"; a value fixes this role's own default in that currency regardless of later exchange-rate movement. This is the "role's per-currency agency default" link in the rate chain — Clients (override, highest priority) and Currencies (exchange-rate fallback, lowest priority) are the other two links. **Only currently-active currencies get a field (2026-09)** — activating a new currency in the Currencies tab makes its field appear here immediately, in both the create and edit forms; a currency that's never been activated shows no field at all, so this list genuinely grows and shrinks with what's active, not a fixed registry.
- **Currencies — a full admin tab.** EUR is fixed (1:1, always active, not editable); any other currency starts inactive and only becomes selectable elsewhere once an admin activates it with an initial "1 EUR = X" rate. An active currency's rate can be updated any time, each update timestamped; a History button (all but EUR) shows the full rate change log. This is the *one* exchange rate the whole app reads for every cross-currency figure — not separately configured per feature. **State explicitly, with a link back to §4, that this is the rate chain's lowest-priority fallback** — the plain EUR-rate × exchange-factor conversion used only when neither a role's own per-currency default (§7.6) nor a client rate-card override (§7.2) applies — mirroring the back-reference §7.6 already carries; don't leave this section reading as if the exchange rate exists in isolation from the cost calculation it ultimately feeds. **Rate-update confirmation (2026-09)** — saving a new rate for an active currency opens a confirmation dialog (old rate → new rate) before it takes effect, explaining explicitly that the change does **not** retroactively affect any offer or project already in the system: each offer's own rate is fixed at creation/last-save time (the same frozen value shown in the offer editor's own Currency field, §4) and only applies going forward to new offers, or to an existing one if it is explicitly re-saved with that currency selected again.
- **Clients, and how per-client cost grids actually work.** The **💲 Costgrid** button on each client row opens that client's *rate card* (an easy label to misread), showing every role with an **Agency default** (read-only) and **Client custom** (blank = use default; a value overrides it for this client only) column, plus one more column per active non-EUR currency. Selecting this client on any offer automatically applies whatever custom rates are set here — the first, highest-priority link in the rate chain. Rate-card management lives **only** here, not in User Administration. **State explicitly, with a link back to §4, that this is the rate chain's highest-priority link** — a client custom rate, once set, wins over both the role's own per-currency default (§7.6) and the plain exchange-rate fallback (§7.7) — the same back-reference treatment §7.6 already gets, so all three links in the chain point at each other and at the one place (§4) that walks through the chain as a whole.
- **Pipeline years and POTs — walked through as a whole:**
  1. **What a POT is, defined before any mechanics:** a Client POT is the total target revenue — the maximum "wallet potential" — allocated to a specific client (or client group) for one forecasting year: existing recurring business plus identified upsell/cross-sell opportunity, combined into one benchmark figure.
  2. **Pipeline years (View A)** — lists every year with a Visible/Hidden badge; a year can be shown/hidden, deleted (blocked if any offer references it), or drilled into for its POTs. Two export links (Proposal Phasing, Project Phasing) sit here too.
  3. **Setting up a target ("+ New POT")** — targets a client, a client group, or one of two general-purpose scopes ("Unassigned / To be Identified", "New Biz"); amount only; year is whichever View B is showing.
  4. **Where progress shows.** The POT banner (total target + achievement % across every POT that year), 5 stage-summary cards (count + fee value per stage, whole-year), and — scoped to one POT — the View Details modal's 4 KPI cards plus a Proposals list. Same progress is also visible from the Pipeline board's detail panel for a linked offer — same number, not tracked separately.
  5. **History.** Every amount edit logged (date, author, old → new value), newest-first.
- **User administration** — the two-step sysadmin promotion/demotion rule (`user → admin` then `admin → sysadmin`; never a direct jump either direction).
- **Terms & Conditions** — every published version retained permanently and viewable, not just the current one; a "👁 Preview" button opens the live acceptance page showing the current draft before publishing.
- **DB Reset's "Reset by scope" is 7 distinct operations, not one clause** — Proposals, Projects & Programs, Clients & Client Groups, Client Ratecards, Actuals, Pipeline Years & POTs, Notifications — each with its own carve-out (e.g. agency-wide ratecards are spared by the Ratecards scope; SIP/Committed proposals are spared by the Pipelines scope). Every destructive action here (all 7 scopes, plus single-proposal delete) requires typing the literal word **DELETE** into a confirmation field.
- **Team (§16.7, 2026-09)** — a standalone directory of allocatable people (name, email, role, job description), separate from PDash user accounts but with an optional link to one. Each resource has one role, picked from the same roles list used in cost grids (shown as "label (code)"; no free-text option — a missing role is created first in Config → Roles); the link is to the role itself, so renaming a role in Config updates its resources, and a role assigned to a resource can't be deleted (2026-09-25). **§10 Notifications**
- **Which channels fire for which trigger (2026-09) — worth a small reference table rather than prose, since the pattern differs by trigger:**
  - *Sharing a project, cost grid, or program with you* — both an email and an in-app notification, for all three resource types alike.
  - *Removing your access to a project* — both an email and an in-app notification (2026-09; previously silent on both channels). This does **not** currently apply to a cost-grid share being removed, which stays silent on both — a real, current gap in the product, not something to describe as symmetric with the project case.
  - *Being made the new owner of a cost grid/proposal* — both an email and an in-app notification (2026-09; previously email only).
  - *An export you requested finishing* — both an email (with the file attached) and an in-app notification to yourself (2026-09; previously email only).
  - *A colleague sending you a "📣 Send Notification" message* — whichever channel(s) they chose (Push, Email, or both) when sending; this is the one trigger where the channel is a real, user-facing choice, not a fixed pairing.
- **Browser (desktop) notifications (2026-09) — a best-effort echo of the in-app bell, walked through as its own small flow:**
  1. A row at the top of the notification panel reflects the current state and re-checks it every time the panel is opened — it's not a one-time prompt that disappears after a decision.
  2. **Permission never asked** — "🔔 Enable desktop notifications?" with an Enable button, requesting the browser's own permission.
  3. **Permission granted, popups on** — "🔔 Desktop notifications on" with a Disable button; Disable is a local, in-app preference (the browser's own permission grant can't be revoked from the page) — re-enabling later doesn't ask the browser again.
